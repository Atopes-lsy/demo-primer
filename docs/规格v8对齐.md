# 零、v9 相对 v8 的改动（1 处）

**v9 全文与 v8 逐行 diff，只有一处实质变化**：第 1.4 节「依据」块的展示形态，
由**常显不折叠**改成**默认折叠**；v9 附录表里对应的那一行同步改了措辞。

| | v8 | v9 |
|---|---|---|
| 依据块默认态 | 常显，不折叠 | **折叠** |
| 折叠态文案 | —（不适用） | `▸ 依据 · 3/6 源命中`，**必须带命中数** |
| 展开态 | 三部分 | 三部分，**顺序不变**：命中来源逐条 → `另 3 源无记录 · 一并列出以示无遗漏` → 未命中的六源清单 |

v9 自己写明改的原因是「**依技术实现方意见改回折叠**」，同时保留一条底线：
**折叠态不能只剩「依据」两个字** —— 否则客服看不出系统查过没有、查到几条，
等于把「底气」的入口也一并藏了。

## 这一处和现有代码的关系：**代码本来就是折叠的**

`frontend/src/components/plugin/AdviceCard.tsx:34` 的 `EvidenceList`
本来就是 `useState(false)` —— **默认折叠**。v8 写「常显不折叠」时，代码和规格是反的；
v9 改回折叠，反倒**把这一处冲突消掉了**。

所以 v9 不新增待办，只留下一个小差距（不是冲突，是文案）：

| 项 | v9 要求 | 现有代码 | 差 |
|---|---|---|---|
| 默认折叠 | 折叠 | 折叠 ✅ | 无 |
| 折叠态带命中数 | `▸ 依据 · 3/6 源命中` | 只有「依据」两个字 ❌ | **要改** |
| 展开态第一段 | 命中来源逐条 | 逐条 ✅ | 无 |
| 展开态第二段 | `另 3 源无记录 · 一并列出以示无遗漏` | `没用上的：⑤ …` ❌ | **要改** |
| 展开态第三段 | 未命中的六源清单 | 依赖 `依据` 数组里凑齐六源 | **要改**（见下） |

第三段值得单说：现在「没用上的」是从 `advice.依据` 里 filter 出来的，
**能不能列全六源，取决于上游有没有把六源都塞进数组**。演示数据里六源是齐的，
所以看着对；真数据一旦某源整条不返回，清单就会静默变短 —— 而这一段存在的
全部意义就是「**以示无遗漏**」。要稳，得按六源封闭集合补空位，而不是 filter。

## 实现时撞出来的一个粒度问题：`N/6` 数的是**源**，`依据` 列的是**条**

v9 新加的 `3/6 源命中` 把一个原来不会暴露的矛盾顶到了台面上：
**计数单位（来源）和列表单位（引用条）不是一回事。**

演示数据里就有两处：

| 位置 | 情况 | 后果 |
|---|---|---|
| `剧本.ts:432` ＋ `:438` | 口径表**一个源**命中两条 —— K06「不良反应处理」＋ K20「投诉与升级」 | 按条计数报成 `2`，但只有一个来源；按源去重则 K20 那条引用被静默吃掉 |

> **原先这里还有第二行**（「`剧本.ts` 里两条都写 `⑥`」）。那一条不是计数单位的例子，
> 是一处**标错的序号** —— 已于 2026-09-29 删掉，见第四节五。

**做法：计数按源，渲染按条。** 两个清单都从六源封闭集合切出来（保证
`命中 + 未命中 = 6` 恒成立，且漏返回的源能补空位列出来），渲染时把该源的所有
条目铺开。这样 `剧本.ts:432/:438` 的 K06 和 K20 **两条都显示**，而计数仍是 `1/6`。

> 演示时如果被问「为什么只有 1/6」：因为口径表是**一个**来源，它贡献了两条引用。
> 这个分数回答的是「六个来源查过几个」，不是「列了几条依据」—— 两个问题别混着答。

## 一处更正（⑨）

我 9/28 写的第 ⑨ 条说：「『列全证明没遗漏』做不到，因为向量召回是 top-K 截断」。

**这条我说错了。** v8 §1.4 的做法是：**列的粒度是「六个来源」，不是「召回条目」**。

```
命中来源逐条列出 → 另 3 源无记录 · 一并列出以示无遗漏 → 未命中的六源清单
```

六个来源是个**封闭集合**，逐个报「有记录／无记录」是可穷举的 —— 所以「证明没遗漏」
**成立**，它证明的是「六个来源我都查过了」，不是「召回没有截断」。

这一改动意味着：**依据清单的骨架不是 top-K 结果，是六源清单**，召回结果填进对应那格。
我原来的担心（top-K 证明不了全集）在「六源」这个粒度上不成立。但更细粒度上仍然成立 ——
「① 商品属性表 查过了」不等于「① 里的每一行都看过了」，这一层限度要在界面上说清。

## 一处措辞冲突：「事实点」被用了两次（2026-10-01 发现）

| 出处 | 界定谁 | 判据 |
|---|---|---|
| §1.2 | 「轮」 | **没写** |
| §二 | 「主张」 | 「能不能单独产出一个输出」 |

## 冲突 4 · 决策树里「拆主张」和「硬触发」谁先

```
v8 §〇：③ 拆主张（按事实点拆） → ④ 硬触发（命中 → 直接转交）
              ↑ 先                            ↑ 后

代码 triggers.py 文档串：硬触发要排在拆主张前面，理由「少一次模型调用就少一个攻击面」
```

v8 §二 还专门强调：「**这是硬性顺序：拆主张必须在判定之前。**」

两边各有理由：
- **v8 的顺序**（拆主张先）：主张是归因单元，先拆才知道风险挂在哪条诉求上
- **代码的顺序**（硬触发先）：硬触发是正则微秒级，能在模型之前挡住注入

**我倾向按 v8**，理由是 v8 的理由（归因）是产品要求，代码的理由（攻击面）**由
`inbound` 安全层已经覆盖了** —— 注入在更前面就被拦了，不需要靠硬触发提前跑。
但这条要说明白，因为它牵动 `triggers.py` 整个模块文档串的论证。

> **✅ 已落，而且是按 v8 落的 —— 但结论比「谁先」更细。**
>
> 实际定下来的是**两层结构**，不是单纯换顺序：
>
> ```
> ③ 拆主张（照样跑，不因硬触发命中而跳过）
> ④ 硬触发 H1–H4  ──命中──→ 整轮转交，⑤ 三层判定整个不跑
>                   └─未命中─→ ⑤ 三层判定
> ```
>
> 两个细节值得记：
> - **`triggers.py` 的论证没有整段删掉**，而是收窄成「H1 命中不短路**拆主张**」——
>   「少一次模型调用就少一个攻击面」这个理由本身是对的，只是它管的是别的事
>   （注入在 `inbound` 就拦了），管不了拆主张。代码里明写「这里原先写错了」。
> - **命中的是「三层不跑」，不是「全链路不跑」。** 顾客情况、拆主张、留痕照常 ——
>   所以矛盾 ① 那句「H1 命中后拆主张跑不跑」的答案是**跑**（为归因），
>   和 `inbound` 原来的说法一致、和 `triggers` 原来的说法相反。
