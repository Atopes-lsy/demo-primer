## 一处更正（⑨）

我 9/28 写的第 ⑨ 条说：「『列全证明没遗漏』做不到，因为向量召回是 top-K 截断」。

**这条我说错了。** v8 §1.4 的做法是：**列的粒度是「六个来源」，不是「召回条目」**。

```
命中来源逐条列出 → 另 3 源无记录 · 一并列出以示无遗漏 → 未命中的六源清单
```

六个来源是个**封闭集合**，逐个报「有记录／无记录」是可穷举的 —— 所以「证明没遗漏」
**成立**，它证明的是「六个来源我都查过了」，不是「召回没有截断」。

这一改动意味着：**依据清单的骨架不是 top-K 结果，是六源清单**，召回结果填进对应那格。
我原来的担心（top-K 证明不了全集）在「六源」这个粒度上不成立。但更细粒度上仍然成立 ——
「① 商品属性表 查过了」不等于「① 里的每一行都看过了」，这一层限度要在界面上说清。

## 一处更正（⑯）

v8 §4.1 的六源编号是：

```
① 商品属性表   ② 口径表   ③ 先例库
④ 订单／物流／售后表   ⑤ 不良反应／投诉记录   ⑥ 补发换货工单的「发出商品货号／名称／数量」＋ 订单的「赠品」字段
```

我在 `types/index.ts` 里写的映射把 ⑥ 写成了「顾客情况」，**错了**。⑥ 是「补发换货工单 ＋
订单赠品」，用途是**判断「这单该发什么、是否已经补发过」**（v8 §4.1 的 2026-09-27 修正说明：
原来这里是「交易快照」，但交易快照不在样本数据里，所以换成了真有的字段）。

# 三、v8 与现有代码正面冲突的四处 ⚠️

**这四条不是「v8 新增」，是同一件事两边理解不同。** 继续写代码之前必须先定死，
否则后面每一步都建在错的基础上。

## 冲突 1 · 「三层判定」的三层，代码写的是另一回事

| | 三层分别是什么 |
|---|---|
| **v8 §四** | ① 系统确认得了吗（**查六个来源**）→ ② 这件事归谁办（**查权限矩阵**）→ ③ 话怎么说（**有承诺／涉个体差异／无**） |
| **代码 `pipeline.三层判定`** | ① 硬触发层（**H1–H4 映射到输出**）→ ② 主张层（**查口径表 K01–K20**）→ ③ 兜底层（**默认客服点发送**） |

**两边毫无重叠。** 代码把「硬触发 → 输出」和「口径表 → 输出」当成了三层里的两层，
而 v8 的三层里根本没有「硬触发」这一层 —— v8 的硬触发是**第 3 步**，在三层判定**之前**
就把事情分流了（命中直接转交，不再往下问）。

v8 的第 ② 层「查权限矩阵」在代码里**完全没有对应的东西**，而权限矩阵是 v8 第六节
整整一节（6.1 能独立办 / 6.2 超额度报备 / 6.2b 转交 / 6.3 必须转交）。这是**最大的缺口**。

v8 的第 ① 层「查六个来源」对应代码里的「依据检索」，但代码把它放在了节点 5、三层判定之后 ——
**顺序也反了**：v8 是先确认有没有，再定归谁办，最后才是表述。

**建议**：`pipeline.三层判定` 按 v8 重写，签名从
`(主张列表, 触发列表, 口径表)` 改成
`(主张, 六源查询结果, 权限矩阵条目, 口径表)`；现有代码降级为其中一小块
（口径表那部分归到第 ③ 层「话怎么说」）。

## 冲突 2 · G2 的含义完全不同

| | G2 是什么 |
|---|---|
| **v8 §五** | **涉个体差异（孕妇／敏感肌）→ 必须带回边界句，不许单独发事实**。理由：只答「不含乙醇」而不带「孕期建议咨询医生」，**等于默认背书** |
| **代码 `guards.G2边界`** | **绝对化措辞词表**（绝对／100%／包退…）＋ **越权承诺正则**（我赔你 50 元） |

**这是两个不同的闸门。** 代码把 v8 里属于 **§9.2 检查二「冲突检测」**的「越权承诺」
塞进了 G2，同时**漏掉了 v8 真正定义的「边界句强制」**。

后果：`G2绝对化硬/软`、`G2越权` 这套东西是我基于旧理解写的（虽然它本身有用，
能拦「保证／一定／绝对」这类措辞），但它**不是 v8 的 G2**。

**建议**：
- 保留现有代码，**改名为 `G2措辞`**（它确实有价值：拦绝对化表述）
- **新增 v8 的 G2 边界句检查**：主张涉个体差异（孕妇／敏感肌／病史）时，
  话术里必须出现边界句，否则判高危「缺边界句」
- 判「涉不涉个体差异」要**读顾客情况小卡，不从主张里抠关键词** —— v8 §二
  明确说了这是为了避免「顾客分两句说就漏了」

## 冲突 3 · H2 和 H4 的去向

| 触发 | v8 §三 | 代码 `pipeline.触发输出表` |
|---|---|---|
| **H2 情绪** | **转交** | **故意不在表里**，注释写着「情绪是语气信号，不决定诉求怎么处置……把它塞进判定表会变成『顾客生气所以转交』，那是错的 —— 生气该安抚，不是推走」 |
| **H4 风控** | **转交** | **报备** |

v8 §三 的表格写得很直白：`H2 | 情绪／信任升级 | ①–⑤ 命中任一即触发 | **转交**`。

v8 §三 还专门解释了为什么 H2 不能设得太松（两个反例：S00009 第 1 句带情绪，
但 `#9「收到了，虚惊一场…券我收下了哈哈」`最后是满意的）。**但那是「阈值该多严」的问题，
不是「往哪个出口」的问题** —— v8 出口定的是转交。

代码里那段注释的论证（「生气该安抚不是推走」）**和 v8 直接对立**。这条得让队长拍板：
按 v8 走（H2 → 转交），还是按代码走（H2 只影响话术语气）。

**H4 没有争议**：v8 说转交，代码写报备，代码改过来即可。

另外 **H1 中危降档**：代码有 `H1降一档 = 报备`，v8 §三 表格里 H1 一律「转交」，没提降档。
需要确认这是代码自作主张还是有依据。

## 冲突 4 · 决策树里「拆主张」和「硬触发」谁先

```
v8 §〇：③ 拆主张（按事实点拆） → ④ 硬触发（命中 → 直接转交）
              ↑ 先                            ↑ 后

代码 triggers.py 文档串：硬触发要排在拆主张前面，理由「少一次模型调用就少一个攻击面」
```

v8 §二 还专门强调：「**这是硬性顺序：拆主张必须在判定之前。**」

两边各有理由：
- **v8 的顺序**（拆主张先）：主张是归因单元，先拆才知道风险挂在哪条诉求上
- **代码的顺序**（硬触发先）：硬触发是正则微秒级，能在模型之前挡住注入

**我倾向按 v8**，理由是 v8 的理由（归因）是产品要求，代码的理由（攻击面）**由
`inbound` 安全层已经覆盖了** —— 注入在更前面就被拦了，不需要靠硬触发提前跑。
但这条要说明白，因为它牵动 `triggers.py` 整个模块文档串的论证。

# 四点五、落地时又发现一处规格漏洞：六源装不下「聊天记录」

按 v8 §4.1 的六源编号去核对演示数据，发现有一类依据**放不进六个格子**：

```
剧本.ts:316  序号: '⑥',  出处: '顾客情况「答应过什么」· 9/26 24:00'
                            ↑ ⑥ 是「补发换货工单＋订单赠品」，不是顾客情况
```

**这不是数据写错，是六源清单漏了一个来源。** H3 逾期判定的依据是「我们承诺过但没做」，
而那个承诺**来自客服话术**（v8 §1.1：「承诺内容 ＋ 时限」的来源写的是
「客服话术里的承诺句 ＋ 提取时限」）。**「聊天记录」不在这六源里。**

v8 §4.1 的六源是：

```
① 商品属性表  ② 口径表  ③ 先例库
④ 订单／物流／售后表  ⑤ 不良反应／投诉记录  ⑥ 补发换货工单＋订单赠品
```

全都是**静态数据表**，没有一个是「对话本身」。但：

- **H3 的依据是客服说过的话** —— 取自聊天记录
- **G4 防矛盾的依据也是客服说过的话** —— 同样取自聊天记录
- 依据块要「证明没遗漏」，那 H3 命中时**这一格必然空着**，看着像「查了六个地方都没记录」

**两个选法，要找队长定**：

1. **加第七源「本会话聊天记录」** —— 最诚实，但要同步改 v8 §4.1 的编号表，
   以及 `EVIDENCE_SOURCE` 的联合类型（要加 ⑦）
2. **把 H3 的依据算在「顾客情况」名下** —— 不用改编号，但顾客情况本身是判定流程的
   **中间产物**不是数据源，「依据来自我们自己的输出」这个说法在留痕上站不住

我倾向第 1 个：留痕的意义就是能追到的事实，追到一个中间产物等于没追。

**暂时没改这行数据** —— 因为两种选法都合理，改了就是替你做了决定。
