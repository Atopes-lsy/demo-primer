## 一 · 为什么是 3c 而不是 3a

3a 要索引的两张表在赛题数据里**都不存在**（xlsx 只有聊天记录／订单／五张工单，
赛题 docx 里「商品属性表」「先例库」「向量」各出现 0 次）。数据由用户另行提供，
在拿到之前 3a 无法开工。

3c 不依赖那两张表：它的输入是判定层已经产出的 `判成`，是纯生成任务。

**而且 3c 是 ③ 先例库唯一可能被读到的地方。** 全仓库 `先例库` 只出现 3 次
（`sources.py` 的文档串、枚举成员、编号→名称映射），**没有任何代码消费它**。
3c 的 prompt 组装给它一个槽，它才有了第一个消费点。

## 三 · 粒度

**一条主张 → 一次生成 → 一句话术。**

依据：`schemas.Advice.话术` 的类型是 `str | None`，**是单数**。本轮可能有多条
主张各判各的输出，但主卡只展示最高的那条，其余留在「本轮处置」里。所以生成是
逐主张的，主卡只是挑一条显示。

`判成.说明` 有一个容易踩的地方（`schemas.Disposition` 写明了）：

> ⚠️ **这句话会原样进右栏，所以它可以给客服看，不能给顾客看。**

第 1 层查不到时的说明文案是「按保守处理交给你判断」这类**对客服说的话**
（v9：顾客永远不该听到「系统查不到」）。**它绝不能出现在话术里** ——
这条要写进 prompt 的硬约束。

## 四 · 规则层两处缺陷（已修）与剩下的一处缝隙

3c 是规则层的第一个下游调用方，写这份设计时撞出**两处规则层自己的缺陷**。
两处都已修，回归测试在 `tests/test_judge.py`。

留档的理由：这两处都不是「3c 缺个工具」，而是**任何人**从 `判成` 往下走都会撞上
的洞 —— 接口线做 `POST /api/判定` 时会撞同一堵墙。已修完之后，3c 与规则层之间
只剩 4.3 一处缝隙。

### 4.1 已修 · `判成.依据` 把六源键丢了

**症状。** `六源结果.记录` 是 `dict[六源, tuple[源记录, ...]]` —— **序号在键上**。
而 `pipeline.py:559` 把它拍平成平元组：

```python
依据 = tuple(r for 组 in 记录.记录.values() for r in 组 if r.exists)
```

`.values()` 丢掉键，`源记录.__slots__` 里又没有序号字段，**丢得没有痕迹** ——
类型上从 `tuple[源记录, ...]` 看不出少了什么。后果是**从 `判成.依据` 出发，
永远说不出一条记录是 ① 还是 ⑤**，而契约里 `Evidence.序号: 六源` 是必填。

**根因不是「忘了填」，是类型注解本身写错了。** `判成.依据` 原本声明成
`tuple[源记录, ...]`，在类型层面就排除了序号能存在。所以修法不是补一个字段，
是**让它产出 `依据条目`** —— `guards.py:43` 那句「字段与前端 `Evidence` 一致」
说明 `依据条目` 本来就是为这件事准备的，`pipeline.py:83` 也早就 import 了它。

**修法**（`pipeline.py`，三处）：

```python
# 1. 判成.依据 的类型与文档串
依据: tuple[依据条目, ...] = ()

# 2. 第 559 行改成 .items()，顺手完成转换
依据 = tuple(
    依据条目(
        序号=str(源),
        出处=f"{r.table} · {r.row_id}" if r.row_id else r.table,
        摘要=r.content,
        用上=r.用上,
    )
    for 源, 组 in 记录.记录.items()      # ← 键在这里，没丢
    for r in 组
    if r.exists
)
```

**修完之后 3c 不再需要 `六源结果` 参数**（原设计的绕行方案作废），也不需要
任何转换模块：`判成.依据` 可以直接喂 `过闸门`，中间没有再丢一次序号的机会。

> `用上=r.用上` 是原样搬运不是取巧 —— 见 6.4。

### 4.2 已修 · `造降级` 的依据恒空

`降级结果.依据` 的文档串写着「客服要判断这句该不该发，**得看得见材料**」，
但签名里根本没有依据可传：

```python
def 造降级(话术: str, 命中: Sequence[object]) -> 降级结果:
    return 降级结果(话术=话术, 原因=tuple(...), 依据=())   # 恒空
```

**这个字段有文档、有意义、没人填。** 修法是补上参数位（不是调用点用
`dataclasses.replace` 绕 —— 那样绕，下一个调用方还会拿到一个静默空的依据）：

```python
def 造降级(话术: str, 命中: Sequence[object], 依据: Sequence[依据条目] = ()) -> 降级结果:
```

默认空元组是**合法取值不是占位**：G3 报「没有任何依据支撑」时依据本来就该是空的。

### 4.3 「放行」不等于「可以 AI 直发」

`是否放行(命中)` 只看高危。而 `待核对`（口径表里业务方没确认的时效数字）是
**中危 + `降级去向` 有值 + `可重生成=False`**：

- `是否放行` → `True`（没有高危）
- `重生成可行` → `True`（中危不参与这个判断）
- **但 `降级去向` 是「客服点发送」**

`guards.py:344-348` 的注释明确要求过这件事：

> 这条已经是中危，不阻断。但「不阻断」不等于「可以 AI 直发」——
> 降级去向照给，否则调用方会把它当成一道普通的提示放过去。

**没有任何现成函数替调用方算这件事。**

**处置：** 3c 的循环出口**同时看 `是否放行` 和 `降级去向`**：
有任意一条命中的 `降级去向` 非空 → 最终去向压到那个值，不许 AI 直发。
函数写在我自己的模块里（`可直发(命中)`），不往 `guards` 里加。

## 五 · prompt 的六块

`开发步骤.md:273` 列了五块（主张／依据／口径的可以说+标准话术／顾客情况／触发），
第六块是 ③ 先例库。

| # | 块 | 来源 | 在 prompt 里的角色 | 强度 |
|---|---|---|---|---|
| 1 | 主张 | `判成.主张` | 要回应的事 | — |
| 2 | 依据 | `判成.依据` | **事实的唯一来源** | 硬 |
| 3 | 口径的「可以说」 | 按 `判成.依据编号` 取 | 上界 | 弱（`一句话进来的流程.md:254` 明说「模型是尽量遵守不是无法违反」） |
| 4 | 口径的「标准话术」 | 同上 | 示例 + 兜底 | 中 |
| 5 | 顾客情况 + 触发 | 装配层 | 语气与紧迫度 | — |
| 6 | **③ 先例库** | `召回先例(主张, k)` | **真人措辞** | 风格 |

**第 4 块和第 6 块不是一回事，必须在 prompt 里说清**：

- 第 4 块是**公司写好的规范话**（20 条固定、全店共用、不带情绪）
- 第 6 块是**真人客服打出来的字**（口语、有称呼、有节奏）
- **照第 4、6 块学语气，照第 2 块写事实。** 先例库只给句式，不给事实。

### 5.1 先例库的硬约束

先例库的内容是**历史同类会话里客服的措辞**，跨买家取材（同一买家只有 2–3 条
样本，当不了 few-shot；138 个会话才够量）。取材时必须避开的两种句子，
否则召回回来当 few-shot，模型照着写就踩闸门：

| 避开 | 否则踩 |
|---|---|
| 带单位的数字（`\d+` ＋ 工作日/小时/天/元/折/ml/g） | `guards.G3来源可查`（`guards.py:159`） |
| 「已 + 动作」的已发生表述（已为您补发／发出／登记／安排…） | `guards.G4防矛盾`（`guards.py:164-166`） |

**为什么先例库不能当「依据」**（这是它 `用上` 恒 `false` 的原因，不是数据偷懒）：

- 回复里的**事实**，真出处是 ① 商品属性表，先例只是二手转述；G3 要按「表名＋
  行号」回查，应该回到 `商品属性表 · XC33002`，而不是回到某个买家的对话
- 回复里的**处理**（「给您补发一个」）是**对那个买家的承诺**，对本案不成立，
  照搬正好命中 G4

所以 ③ 在 `Evidence` 里 `用上: false` 是**正确语义**：它是风格来源，不进事实依据。

## 六 · 循环

```
组装 prompt（第一次不带反馈）
  ↓
LLM → 话术
  ↓
guards.过闸门(话术, 依据, 可引用, 已发出, 顾客情况, 待核对, 涉及个体差异)
  ├─ 放行 且 无降级去向           → 定稿
  ├─ 重生成可行(命中) 且 已试 < 2 → 把高危命中塞回 prompt，重来
  └─ 否则                        → 降级
```

**重试封顶 2 次是硬要求**（`开发步骤.md:277`）。理由在 `guards.重生成可行` 的
文档串里：G3「没有依据」和 G4「谎称已做」判 `可重生成=False`，重生成只会把模型
困在原地转圈，或者教它换个说法把同一个谎绕过去。

**「2 次」指重试 2 次，不是总共 2 次** —— 初次 + 2 次重试 = **最多 3 次模型调用**。
`开发步骤.md:277` 的「最多 2 次」两种读法都通，这里定死为前者，测试按 3 次断言。

**重试时只喂高危命中。** 中危不阻断，喂进去会让模型去改本来没问题的句子。

### 6.1 反馈的形状

`闸门命中` 自带喂回去需要的全部字段，不用另造结构：

```
闸门 / 名称 / 严重度 / 详情 / 证据 / 建议
```

喂给模型的是「上一稿 + 这几条意见」，措辞要说明**这是修改要求不是新任务**，
否则模型会另起一句全新的。

### 6.2 降级

`pipeline.造降级(话术, 命中, 依据=判成.依据)` 造包裹。`依据` 是 4.2 新加的参数位 ——
降级的终点不是空白，客服得看得见材料才知道该补什么。

降级的终点不是空白（`pipeline.py:636`）：

> 把最后一次被拦的原文连同命中原因给他，改比写快，而且改出来的版本天然避开了
> 已经指出的坑。

### 6.3 入口签名与参数来源

`过闸门` 的参数**逐个定死从哪来**，别让实施时各猜一套：

> `过闸门` 一共**八个**参数。下面七个是 3c 要管的；第八个 `路径` 是 `koujing.json`
> 的**文件路径**（`koujing.py:119`），不是语义参数 —— 3c 不传，走默认的
> `data/koujing.json`。只有测试要注入另一张口径表时才传它。

```python
def 生成话术(
    判成,                                  # pipeline.判成 —— 依据／依据编号／涉个体差异都在它上面
    顾客情况: Sequence[tuple[str, str]],    # (标签, 值) 对，装配层给
    触发列表: Sequence[object],            # triggers.触发
    口径表: 口径表数据,                     # koujing.加载口径表()
    已发出: Sequence[str],                 # pipeline.已发出的话(消息, 本轮之后)
    召回先例=召回先例,                      # 注入点，见 5.1 / 九.2
) -> 生成结果
```

**原设计里还有一个 `六源结果` 参数，4.1 修完之后删掉了。** 它当初存在只是为了
从字典键上取序号，而那件事现在 `判成.依据` 自己就带着。少一个参数，也少一处
「传进来的 `六源结果` 和 `判成` 不是同一轮」的可能。

返回值：

```python
@dataclass(frozen=True, slots=True)
class 生成结果:
    话术: str
    去向: 输出类型
    """**可能和 `判成.输出` 不同。** 降级压低（4.3）会让 AI直发 变成客服点发送。"""
    命中: tuple[闸门命中, ...]
    """最后一次的闸门结果，进 `判定响应.闸门`。"""
    用到的依据: tuple[str, ...]
    """模型自报的出处，如 `("口径表 K01", "不良反应工单 · BLFY70604980")`。

    右栏拼 `Evidence.用上` 用它，**不是** `源记录.用上` —— 见 6.4。
    """
    降级: 降级结果 | None = None
    """非 None 表示走到了降级，`话术` 是最后一次被拦的原文。"""
    调用次数: int = 1
    """调了几次模型（1–3）。**留痕要记** —— `开发步骤.md:325` 要求留痕能回答
    「闸门拦了几次、重生成试了几轮」。不在这里带出去，留痕层就查不到。"""
```

| `过闸门` 参数 | 从哪来 |
|---|---|
| `话术` | 本次模型输出 |
| `依据` | `判成.依据`，`用上` 归一为 `True` 后传（4.1 修法 ＋ 6.4） |
| `可引用` | **口径表的「可以说」＋「标准话术」原文**，按 `判成.依据编号` 取（`guards.py:281` 规定的语义） |
| `已发出` | 调用方传（`pipeline.已发出的话`） |
| `顾客情况` | 调用方传，原样转给 `G4防矛盾` 找「办过什么」行 |
| `待核对` | `口径表.待核对数字()`（`koujing.py:62`） |
| `涉及个体差异` | `判成.涉及个体差异` |

**`可引用` 只影响 G3 的数字校验**，不参与 prompt 组装。所以同一份「可以说／
标准话术」文本会走两条路：一条进 prompt（第 3、4 块），一条进闸门（`可引用`）。
两处必须是**同一份原文**，别取不同的字段 —— 取岔了会出现「prompt 里能说、
闸门说数字没出处」这种自相矛盾。

**`可直发(命中)` 放 `app/llm/话术生成.py`**（4.3 那个函数），不往 `guards` 里加。

### 6.4 「用上」的两套取值

`源记录.用上` 的语义是「**本轮话术有没有引用它**」（`sources.py:64`），而
**生成话术的时候话术还不存在** —— 这里有个鸡生蛋：G3 要拿 `用上` 判「有没有
依据」，可它判的时候话术刚出来，用没用在定义上还没定。

先看 G3 究竟拿它干什么（`guards.py:291`）：

```python
用上的 = [e for e in 依据 if e.用上]
if not 用上的:
    → 高危「这句没有任何依据支撑」、可重生成=False、降级
```

**它是载重件不是装饰。** 注意下面那个数字校验（`可查文本 = 摘要 ＋ 出处`）用的是
**全部** `依据`，只有这条判空按 `用上` 过滤 —— 所以 `用上` 在 G3 里只回答一件事：
**这批依据算不算「有材料」。**

拆成两套，别混：

| | 取值 | 由谁定 | 为什么 |
|---|---|---|---|
| **过闸门时** | **归一为 `True`** | 3c 在调 `过闸门` 前统一置 True | G3 那一问的意图是「检索有没有召回到材料」（`guards.py:277`），问的是**检索**不是**引用**。而「检索有没有召回到」`判成` 第 1 层已经认证过了（`有记录()`）—— 归一之后两处判据一致；不归一，`用上` 只要全是 False，G3 每次都判「没有任何依据」 |
| **进右栏时** | **模型自报** | `生成结果.用到的依据` | `命中源()` 数的是它，右栏那个 `N/6` 和「未命中的六源清单」都由它决定 |

**坑的根在于两个谓词本来就不一致：** `有记录()` 只看 `exists`，`命中源()` 看
`exists and 用上`。`判成` 第 1 层走前者，G3 的判空走后者。3c 归一 `用上` 就是在
弥合这个差 —— 否则会出现「`判成` 说 AI直发、G3 说没有任何依据」这种自相矛盾的结论。

**而 `判成.依据` 里的 `用上` 原样搬运 `源记录.用上`**（4.1 的修法），因为
`六源结果.命中源()` 自己就用它数 `N/6`，搬运才能让两处计数一致。检索层**判不了**
用上（话术还没生成），保持默认 `True` 即可。真正决定 `Evidence.用上` 的是模型自报。

**模型自报要是空的**，而话术又确实写出来了 —— 那正是 G3 该拦的形态（说了事实
却没有依据）。两套取值并存不是权宜：它们在回答两个不同的问题，只是共用了
`用上` 这一个字段名。

### 6.5 转交不归 3c 管

`输出 == 转交` 的话术由 `app/rules/handover.py` 的 `转交话术表` 提供
（6 类各一句，已实现）。3c **只负责 `客服点发送` 和 `AI直发` 两种去向**。

理由：转交话术必须走 ② 客服点发送（含时限即承诺），而且它们的三条硬边界
已经写在 `handover.py` 的导入自检里。让 LLM 重新生成一遍，等于把那三条边界
再赌一次。

## 九 · 记下的坑（不阻塞，别忘）

1. **K01 的「标准话术」自相矛盾。** 它写的是「孕期可以正常使用」，而 K01 自己的
   禁语里就有「孕妇可以用」，`禁语模式` 是空的。G1 查的是字面短语，
   **这句能溜过去**。所以「标准话术天然不含禁语」（`开发步骤.md:200`）在 K01 上
   不成立 —— **3c 不能拿它当兜底直接发**。`剧本.ts:143` 那句演示话术是把它删掉
   之后的结果。
   > 这属于 ② 口径表的数据问题，不在模型线范围。已报给决策线。

2. **③ 先例库的数据还没到。** 接口先冻结（`召回先例` 注入，默认返回空列表），
   拿到数据再接。空列表时 prompt 少一块，不报错。

3. **3a 的向量检索可能是负优化。** `开发步骤.md:250` 自己说了「口径表只有 20 条，
   不走向量，向量召回在 20 条上是负优化」。而 ① 商品属性表只有 **20 个货号**，
   量级一样。先用全量塞 prompt，等 ①③ 的真实体量出来再决定要不要上 pgvector。
   > 但注意：①③「走 top-K，源内做不到没有遗漏」是演示时主动要说的一层限度
   > （`types/index.ts:357`、`开发步骤.md:257`）。**改全量扫描会让这套说法失效**，
   > 要一并想清楚怎么说。

4. **`先例库` 的语义改动未落地。** 本设计把 ③ 定为「跨买家同类场景的真人措辞」，
   `sources.py:7` 的文档串和演示文案里还没有这句话。**改动在 `app/rules/`
   和前端，不是模型线的文件**，由对应那条线做。

5. **③ 的记录和 `源记录.content` 的措辞对不上。** `content` 的定义是「这一条
   提供的**事实**。第 3 层出稿时的唯一事实来源」（`sources.py:62`），而 ③ 提供的
   是**句式**。机械上跑得通（③ 的 `用上` 恒 false，它的 `content` 不会被当事实
   引用），但**文档串这句话在 ③ 上是失效的**。
   演示时被问到别硬说「③ 也是事实来源」。
   > ⚠️ **但 ③ 的 `content` 仍然会进 G3 的可查文本。** `guards.py:308` 拼的是
   > **全部**依据的摘要＋出处，**不按 `用上` 过滤** —— 所以 ③ 里若留着带单位的
   > 数字，它会给话术里同一个数字**背书**，而 ③ 根本不是事实来源。
   > 这正是 5.1 要求取材时滤掉数字的原因：那道过滤是**载重件**，不是审美。
   > 要彻底理顺得改 `sources.py`，和上面第 4 条一起做。

6. **③ 单独命中时，第 1 层会判「查得到」。** `六源结果.有记录()` 只看 `exists`，
   不看是哪一源 —— 一条主张若**只有 ③ 先例库**有记录，第 1 层照样放行，
   而 ③ 给的是句式不是事实。6.4 把 `用上` 归一为 `True` 之后，G3 的「有没有材料」
   也会跟着认账。

   > **这是第一层的判据问题，不是 3c 的。** 修法在 `sources.有记录()` 或规格
   > §4.1（比如要求「至少一源不是 ③」），**不要在闸门里给 ③ 开特例** ——
   > 闸门一旦和 `判成` 用不同的谓词，就会出现「判成说 AI直发、闸门说没依据」
   > 这种自相矛盾的结论，那比漏洞本身更难查。
