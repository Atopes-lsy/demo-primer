## 一 · 三道闸

`输出类型.AI直发` 现在**不可达**。堵它的不是一个东西：

| # | 闸 | 在哪 | 症状 |
|---|---|---|---|
| 1 | `六源=None` | `pipeline.三层判定` 签名 | 每条主张取 `空六源结果` → 第1层永远「查不到」 |
| 2 | `认口径函数=lambda _: None` | 同上，**同一行** | `依据编号` 静默全空，右栏挂不上「依据：口径表 K10」 |
| 3 | **H3 逾期整轮短路** | `三层判定` 里 H3 那个早返回 | **三层判定根本不跑** |

**第三道是这次核出来的，也是要命的那道。**

`H3逾期(承诺时限, 当前)` 读的是**会话状态**，不是消息。而演示的两条线**共用同一段历史**
（`剧本.ts`：「两条线共用的那段历史」，承诺 9/25「48 小时内发出」、时限 9/27、今天 9/29）
—— 所以 `S_DEMO_A` **全程每一轮都命中 H3**。

于是 `三层判定` 每次都从 H3 那个早返回走掉，整轮报备。**六源接不接、认口径换不换，都没有区别。**

而剧本里 线一 **同一会话、同一天**，既有一格 `层: '硬触发'`（H3 → 报备），
又有一格 `层: '第3层'`（`含乙醇` → AI直发）。**两者不能同时成立。**

> **这条也解释了为什么 `开发步骤.md` 的验收表看起来自相矛盾。**
> 那张表里 `S_DEMO_A` 第 1 轮写「本轮处置 ①＋②＋③，硬触发 H3」——
> 在现在的代码下不可能出现。

## 二 · 两个已拍的决定

### 2.1 H3 不短路，只提示

**H3 照常进 `触发[]` 和留痕，说明里强制「开头必须先道歉」，但不阻止三层跑。**

理由（记下来，下一轮的人会问）：

- v9 §三 的短路名单本来就是 `H1/H2/H4` —— **H3 不在里面**。代码里 `短路触发` 那个
  `frozenset` 也只有这三个；H3 的短路是**另一个地方**单独写的。
- v9 给 H3 的原话是「高优先级报备（对话**还在客服手里**）」——
  整轮报备恰恰是把对话冻住，和这半句相反。
- 逾期是「这一单的事」，不是「这一轮所有主张的事」。

### 2.2 六源不上 pgvector

| ③ 先例库 | **赛题数据里没有** | 0 |

## 三 · 改哪几处

`rules/` 归模型线（2026-10-01 已定），下面**四处**都在本线内。
接口线只负责在 `api/路由.py` 里把函数**传进去**。

> **`3.4` 是初稿漏掉的**，补上来之后这单才是「让 `/api/判定` 能跑」的完整清单。
> 前 3 项是「判得对」，第 4 项是「判得起来」。

### 3.1 `pipeline.三层判定` —— 拆掉 H3 早返回

现在长这样（`h3 = next(...)` 那个分支）：

```python
h3 = next((t for t in 触发列表 if t.编号 == 触发编号.H3), None)
if h3 is not None:
    return [判成(主张=m, 输出=H3去向, 说明=f"...开头必须先道歉", ...) for m in 主张列表]
```

**要做的**：去掉这个早返回，把「开头必须先道歉」变成一条**提示**送到 `_判一条` 里，
由它拼进每条主张的 `说明`。三层照跑。

⚠️ **`短路触发` = `{H1, H2, H4}` 那个分支一个字都别动** —— H1/H2/H4 的整轮短路是对的，
v9 §三 点名了它们，理由（「对话都转出去了」）成立。这次只拆 H3。

### 3.2 `permissions.E05` —— `可认: False` 要翻过来

**这是 3.1 的连带后果，不做的话会判歪。**

`E05 客服承诺逾期未做（我方还能补）` 现在：

```
去向 = 报备        ✅ 对的
可认 = False       ← 要改成 True
关键词 = ()        ← 要填
```

它的 `依据` 栏自己写着：**「§6.2；与 §三 H3 是同一件事，去向也一致」**。
—— 也就是说，**它故意不可认，因为 H3 替它挡在前面了**。H3 一不短路，它就得接管。

**不做的后果**（实测过）：`逾期未发货` 走第2层返回**「未列明」**，
继续到第3层 → 有承诺 `False`、个体差异 `False` → **判成 `AI直发`**。
「答应过的事没做到」被 AI 直接发出去，这是最不该自动发的一类。

**关键词建议 `('逾期',)`。** 别加「未发货」—— 线二的 `赠品未发货` 含这三个字，
会被误认到 E05。它现在正确地落在 `L03 赠品／小样追加` 上（`可认: True`、限额 1 件，
但**件数未知** → 判不了 → 说明「走报备核实」），那个结果是对的，别弄坏。

实测过：只加 `逾期` 的话，演示那五条主张**各只命中一条**
（`含乙醇`、`孕妇能否用` 零命中），`逾期未发货 → E05 → 报备` 走得通。

### 3.2b `permissions.查权限` 的说明模板 —— 「须转交」是写死的

**同一处改动的第二个连带后果，比 3.2 更隐蔽。**

`permissions.py` 里「没超额度」那条出口：

```python
if 条目.去向 is 权限去向.在权限内:
    说明 = f"在权限内：{条目.事项}（{条目.限额}）"
else:
    说明 = f"{条目.事项}：{条目.层级}处理，须转交"     # ← 把去向假定成转交了
```

对 Z 系七行是对的（它们全是转交），**对 E 系是错的** —— `E01`–`E05` 去向都是**报备**。

现在看不出来，因为 E 系全部 `可认: False`，这个分支根本走不到。
**3.2 一改，E05 就走进去**，实测输出：

```
去向=报备   说明=客服承诺逾期未做（我方还能补）：一线处理，须转交
```

**去向和说明互相打架。** 右栏上「报备」和「转交」是两个不同的按钮，客服照哪个做？

**要做的**：说明跟着 `条目.去向` 走。

| `条目.去向` | 说明 |
|---|---|
| `在权限内` | `在权限内：{事项}（{限额}）` ← 原样不动 |
| `报备` | `{事项}：{层级}处理，须报备` |
| `转交` | `{事项}：{层级}处理，须转交` ← 原样不动，Z 系不受影响 |

按**去向**分支，不要把 E05 的编号硬塞进 if —— 同节还有 `E01`–`E04` 三条同病。

### 3.3 新建两个目录

按 `面试.md` 的文件所有权，这两个目录是模型线的，现在**都不存在**：

```
backend/app/检索/    ← 新
backend/app/llm/     ← 新
```

三个文件：

| 文件 | 导出 | 干什么 |
|---|---|---|
| `检索/商品表.py` | `装商品表(路径) -> 商品表`、`查商品(商品表, 货号)` | 读 ①，按货号索引 |
| `检索/六源.py` | `查六源(主张, 会话, 商品表) -> 六源结果` | 六源逐个查 |
| `llm/认口径.py` | `认口径(主张, 口径表) -> str \| None` | 20 条全塞 prompt 让模型认 |

**`查六源` 的签名固定成这样**，因为 `三层判定` 的 `六源` 参数是**按主张索引**的
（`{主张: 六源结果}`）：

```python
查六源(主张: str, 会话: schemas.Session, 商品表: 商品表) -> 六源结果
```

调用方对每条主张调一次，拼成字典传进去。

⚠️ **`六源结果.记录` 必须带齐六个键。** `__post_init__` 会拦漏键的，
别绕过它 —— 用 `空六源结果(主张)` 起手再逐个填。这条是有意的：漏一源会让右栏的
分母从 6 变成 5，**看上去还是「N/N，没遗漏」，查不出来**。

### 3.4 `llm/拆主张.py` —— 没有它，判定跑不起来

**这是第四个模型位，也是最先要跑的那个。**

`三层判定` 的入参是 `主张列表: Sequence[str]` —— 那个列表**全项目没有任何东西产出它**。
`pipeline.py` 里没有，`路由.py` 里也没写。`tests/test_judge.py` 那些测试全是拿
字面量喂进去的，所以测试全绿也掩盖不住这个洞。

规格在 `docs/一句话进来的流程.md` 的「节点 3 · 拆主张」：

```python
拆主张(消息: str, 顾客情况) -> list[str]
```

- **输入**：买家消息 ＋ 顾客情况
- **输出**：主张列表。`Disposition.主张` 是它的最终落点
- **选型**：LLM ＋ 结构化输出（JSON Schema / function calling 约束成数组）。
  一句话里可能同时有「问成分」「要补发」「投诉」三件事，**规则拆不开**
- **粒度**（2026-10-01 已定义）：一条主张 ＝ 一个**事实点** ＝ 一个能独立处置的点。
  「含乙醇」和「孕妇能用」是**两条** —— 它们是否属于同一**诉求**是节点 3.5 的事，
  **不影响条数**

⚠️ **`拆主张` 在 H1 命中时也要照跑**，别短路它。`triggers.py` 文件头专门为这件事
写了注（「这里原先写错了」）：风险要**归到哪一条主张上**才有的展示，不拆就没有归因单元。

⚠️ **主张文本就是主键。** 前端拿它当 React key（`key={d.主张}`），
同一轮里两条主张文本相同就会冲突。让模型输出时**别产生重复项** ——
这个坑不会报错，只会让右栏少显示一条。

**谁先做**：3.4 是上游，3.1／3.2／3.2b／3.3 都排在它后面。
但它和其他几项**没有代码依赖**，可以同一个 PR 里一起下。

| 源 | 怎么查 | `table` / `row_id` | `content` |
|---|---|---|---|
| ① | `会话.订单.商品货号` → 查商品表 | `"商品属性表"` / 货号 | 见 4.1 |
| ② | 复述 `认口径` 的结果 | `"口径表"` / `K10` | 该条的 `标准话术` |
| ③ | **恒空**（赛题数据里没有先例库） | — | — |
| ④ | `会话.订单` 存在，且主张涉发货／物流／签收 | `"订单"` / 订单号 | 订单状态等 |
| ⑤ | `会话.工单.kind == 不良反应`，且主张涉健康 | 表名 / 工单号 | 工单摘要 |

> **2026-10-06 追记 —— ③ 那一行仍然填「恒空」，但原因变了。** 写它的时候，
> 原因是「赛题数据里没有先例库」；**现在库有了**（139 条，`data/先例库.json`，
> 2026-10-05 建），③ 恒空成了**设计**：它**不进六源**（`开发步骤.md` §7.1 §丙）——
> 先例是风格来源，走 prompt 第 6 块，不是事实依据。**别因为「有库了」就去把
> ③ 填进六源**：`有记录()` 只看 `exists`，③ 一旦进六源，「只有先例查得到」的
> 主张会在第 1 层判「查得到」，判定结果整个会动。

⚠️ **`exists` 和 `用上` 不是一回事，别填成一个。**
`六源结果.有记录()` 看 `exists`（决定**第 1 层**走哪条路）；
`命中源()` 还要看 `用上`（只决定**右栏那个 N/6**）。
填错的后果不对称：`用上` 填错只是分数虚高，`exists` 填错是**放行一条没依据的话**。

**④⑤⑥ 的相关性判断先用关键词**，和 `认权限` 同一路数 —— 认不出就不记，
**别为了凑 `N/6` 硬塞**。这一层宁缺勿滥：多记一条只是分数好看，
少记一条是第 1 层判成「查不到」→ 落客服点发送 → 保守但安全。

### 4.1 ① 的 content 有一个具体的坑

演示那句话是「亲，这款**不含乙醇**哦～」。我查了 `XL10302 测试修护精华液30ml`：

- `成分表（完整）` ＝ 水、甘油、丁二醇、透明质酸钠、泛醇、积雪草提取物、
  神经酰胺NP、角鲨烷、卡波姆、黄原胶、香精、苯氧乙醇 —— **里面没有乙醇**
- `不含（可对顾客说）` ＝ 不含：维A类（视黄醇）、水杨酸、对苯二酚、二苯酮-3、皂基
  —— **里面也没有乙醇**

**所以「不含乙醇」只能从 `成分表（完整）` 做否定判断得到，`不含（可对顾客说）` 那一列帮不上忙。**
照 `不含` 列去匹配会查空 —— 这是本单最容易踩的一脚。

**content 至少拼这五列**（演示两条主张都落在这上面）：
`商品名称` / `成分表（完整）` / `不含（可对顾客说）` / `孕妇慎用成分` / `不适用/需谨慎`。

**依据是站得住的**：化妆品按法规要求全成分标注，所以「全成分表里没有」＝「不含」。
被问到就这么答。

> 剧本里那条依据写的是「商品属性表 · **成分栏**」—— 表里没有叫「成分栏」的列，
> 指的是 `成分表（完整）`。前端那份是演示文案，不用改。

## 五 · 谁把它接上

**接口线。** 模型线只出函数，`api/路由.py` 是接口线的文件。

**签名冻在这里，两边照它各写各的**（前端照 `schemas.py` 写是同一个道理）：

```python
拆主张(消息: str, 顾客情况) -> list[str]
查六源(主张: str, 会话, 商品表) -> 六源结果
认口径(主张: str, 口径表) -> str | None
```

接起来是这几行：

```python
主张列表 = 拆主张(消息, 顾客情况)
六源 = {m: 查六源(m, 会话, 商品表) for m in 主张列表}
判成 = 三层判定(
    主张列表, 触发列表,
    六源=六源,
    顾客情况=顾客情况,
    口径表=口径表,
    认口径函数=lambda m: 认口径(m, 口径表),
)
```

**接口线不用等这三个函数落地。** 照签名把 `/api/判定` 的架子先搭完 ——
装载会话、取轮次、输入安全、硬触发、`收敛`／`主卡形态`／`造降级`、组响应，
**一段都不碰模型位**。函数一落地就通，届时只需要删掉临时的 import 占位。

⚠️ **别在接口线里写这三个函数的临时实现。** 要跑通用 `unittest.mock` 或
一个 `_假拆主张` 之类的私有桩，**别放进 `llm/`／`检索/`** —— 那是模型线的目录，
两边各写一份就是四线规则要避免的那个错。

⚠️ **两个参数在同一行，别只传一个。** 只传 `六源` 的话第 1 层通了、
`依据编号` 还是空的 —— 而右栏少一行**不会报错**。

**`认口径` 换模型**：口径表只有 20 条，**每次全塞 prompt，让模型选编号或返回 `None`**。
不要走向量（20 条上是负优化），也别去调分词。
输入给：主张 ＋ 20 条的 `编号` / `话题` / `可以说`。

**认不出就返回 `None`，不要猜一个。** `依据编号` 空着比挂错强 ——
挂错了客服对不上账，而且**不会有任何东西报错**。

> 现有的 `pipeline.认口径` 是关键词匹配，**实测 5 条真主张 0 条认得出**
> （`开发步骤.md` §一 有那张表）。它是「话题名按 `()/` 切段后做子串匹配」，
> 所以「孕妇能否用」认不出 K01（K01 的话题名里是「孕期」），
> 「含乙醇」认不出 K10（K10 是「成分安全(酒精/香精)」）。
> **别花时间修关键词，直接换模型。**
