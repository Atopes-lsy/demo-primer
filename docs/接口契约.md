# 接口契约

「一句话进来 → 右栏出什么」的 JSON 形状。

**代码是 `backend/app/api/schemas.py`，这份文档给它配人话。** 两边说的是一件事，
不一致时以 `schemas.py` 为准 —— 它有测试跟着跑，文档没有。

> 本文里那个样例 JSON 是**测试真的会去解析**的
> （`tests/test_schemas.py::test_接口契约文档里的样例能通过校验`）。
> 随手改一改字段名不会有人发现，但改坏形状会当场变红。

---

## 一 · 三条规矩

**1 · 字段名逐字照 `frontend/src/types/index.ts`，两边一字不差。**

中文名、大小写、可选性全照抄，**不引入映射层** —— 后端叫什么，线上就叫什么。
这是 `docs/开发步骤.md` 步骤 0 的完成标准，由 `tests/test_schemas.py` 逐字段核对：
它**真的去解析那个 TS 文件**，不是在这儿手抄一份再跟自己比。

为什么值得专门修一道防线：两边字段名漂移**不会让任何东西报错**。后端多拼一个字、
前端读 `undefined`，界面只是少显示一块 —— 直到演示当天有人问「这儿怎么是空的」。
这是唯一一类「两边都编译得过、两边都测试通过、合起来却是坏的」的错。

**2 · 枚举从 `app/rules/` import，不另抄一份。**

`输出类型` / `类别` / `处置` / `触发编号` / `六源` 都有现成的 —— 这五个
`schemas.py` 直接从 `app/rules/` import（`schemas.py:34-37`），测试用 `is` 断言
「就是规则层那个对象本身」，专拦「抄了一份、恰好值一样」。

⚠️ **`权限去向` 不在这一组里**，别照抄这句话去 import 它 —— `schemas.py:218`
声明的是 `str`，值域靠字样对齐（见 `app/rules/permissions.py`），没有 `is` 断言。
这是**有意的取舍**：它是个开放集合，加一个去向不该要动三个文件。

**3 · 别名只在 Python 语法不允许时用。**

四个带括号的金额列（`单价(元)`、`实付金额(元)`、`退款金额(元)`、`订单实付(元)`）
不是合法的 Python 标识符，只能换个属性名再挂 `alias=`。

**这不是映射层** —— 线上跑出来的键就是 `单价(元)`，和前端一模一样。
`契约模型` 上设了 `serialize_by_alias=True`，所以不带参数调 `model_dump()`
也走别名。这一条是防一个具体的坑：默认走属性名的话，前端读到 `undefined`
**而且不报错**，界面上只是少了一个数字。

### 路径带 `{id}`，而且**花括号里的名字必须是 ASCII**

原来那张表写的是 `/api/报备`，不带 id。落地时改成 `/api/会话/{id}/报备`：
四个按钮**都在某个会话里按**，而 `判定` 的产物（台账）本来就是按会话存的。

⚠️ **路径参数只能叫 `{sid}` 这种 ASCII 名，不能叫 `{会话ID}`。**
Starlette 认参数的 `PARAM_REGEX` 是 `[a-zA-Z_][a-zA-Z0-9_]*`，匹配不上中文名，
于是那一段被当成**字面量**编译进路由正则 —— 打过来的
`/api/会话/S_DEMO_A/报备` 匹配不上 `/api/会话/{会话ID}/报备` 这个字符串，
**整个路由 404**，报错是「Not Found」，看着像路由没挂上，而两条都不是。
中文段（`/api/会话/`）本身没问题，只有**花括号里的名字**受这个限制。

### `草稿检查` 不建，禁语比对留在本地两道

原表这一行排的是「输入框每次编辑后打后端比一次」。**2026-10-03 拍掉，不建。**

- 禁语**每次编辑后**都要重查（前端自己的注释就这么写的），每按一次键一次往返
  不值当 —— 而这一条的收益只是「多一次往返」；
- `schemas.Session` 刻意不声明 `草稿` 字段（§四 第 2 条），方向是同一个：
  **草稿是输入框里的字，后端不管它。**

代价写在明处：前端读的 `data/koujing.ts` 和后端那份 `koujing.json`
**不是同一份**（`koujing.json` 还落后 v4 定稿），所以「本地和后端是同一套规则」
这句话现在**不成立**，别当已成立的事实说出去。

### `/api/会话列表` 每条会话都带 `顾客情况`（2026-10-03）

**在这之前，140 条会话的 `顾客情况` 一律是 `null`。** 于是除两条演示线之外，
点开哪一条右栏都只有一句话（「这条会话还没跑判定」）—— 用户看到的是
**插件模块整块没出现**，而不是「模块在、判定还没接上」。

现在 `路由.会话列表` 给每条都装配一遍五行（`判定.整会话顾客情况`）。
实测（当天）：140 条、5.8ms、响应体 850KB → 913KB。
（**条数和体积同一天又动过一次** —— 合并窗口，见下一节。契约的字段那一块
也在那一节里加了两个，本节的「字段一个没加」只对当时那一刻成立。）

**这不是「给 138 条真会话跑了判定」。** 判定仍然只接在两条演示线上。
变的是「顾客情况」这一栏从空变成了装配得出来的那五行，右栏因此是
**顾客情况有内容 ＋ 下面照实说还没跑判定**。`建议` / `本轮处置` / `闸门`
一个都没产出，仍然是 `null` / 空。

| 装配的是第几步 | 跑不跑 |
|---|---|
| 4 装配基础行 | ✅ |
| 5 硬触发 | 🟡 **只算 H3** —— 见下 |
| 6 回填 `警示` | ✅ |
| 7 拆主张 及以后 | ❌ 一次都不跑 |

三处与整条判定**故意不一样**，逐条：

1. **切轮不走模型。** `归属` 传 `None`，退回纯结构切法（买家发言开始一轮、
   客服或 AI 收尾）。判定那条路的 `归属` 是 `认诉求` 一条买家消息一次认出来的
   —— 114 个窗口就是几百次调用，而这是一个一进页面就打的接口。
   **两边切出来的轮可能不同，但这五行上一个字都不差**：唯一用到轮的是
   「这次要什么」，而它 2026-10-04 起是**攒**的（`装配.这次要什么`）——
   轮怎么切不影响拍平之后的顺序和内容，只有「切到哪一段」和「去不去尾」
   （`已说完`）影响它。
   退回结构切法不等于「第三种切法」：`认诉求` 够不着模型时给所有消息同一个标签，
   `切轮` 收到的正是这个结果（`pipeline.切轮` 的文档串）。
2. **只算 H3 一个硬触发。** H1／H2／H4 的产出只喂 `三层判定` 的主卡，这条路
   不跑判定，那个产出在右栏没有落点。H3 是四个里唯一**回填进顾客情况**的
   （`pipeline.组装顾客情况`），所以这不是「挑一个算」，是「只算有落点的那个」
   —— 结论和跑完整条判定**逐字相同**，另外三个改不了这五行。
3. **「现在」取会话最后一条消息的时间**（`会话.最近时间`），不是真实时钟。
   取真实时钟就会把 2026-09 的数据放到**录制当天**的天平上称，屏幕上出现
   「9/27 承诺，已逾期 8 天」而旁边每行别的日期都是九月（`台账.py` 顶上也记着
   这个坑）。取会话自己的末刻，判的是「**这条会话结束的时候，那个承诺就已经
   过期了**」—— 数据内部就有的事实，且同一条会话每次请求答得一模一样。
   `最近时间` 解析不动时**跳过 H3、不给警示**，退回真实时钟会让一条解析不动的
   会话凭空多出一个逾期天数。

**两条演示线不受影响。** 前端 `合会话列表` 把 `S_DEMO_A` / `S_DEMO_B` 整条
换成 `剧本.ts` 那份（右栏内容全由播放进度驱动，格 0 就是「还没开始演」），
接口这一份**一个字段都不读**。所以演示镜头一个都没动。

### `/api/会话列表` 按顾客合并窗口，`Session` 加两个字段（2026-10-03，同一天）

**138 条真会话 → 112 个窗口**，加上两条演示线，这个接口现在返回 **114 条**。

**为什么合。** 右栏那五行「顾客情况」本来就是**以前的会话攒出来的** ——
「这是谁」的备注写着「上次 5/6 · 补发登记」、「答应过什么」扫的是客服历史上
许过的诺、「办过什么」「这单」读的是挂在会话上的工单和订单。可数据是按会话
给的：同一个人在 5/5、5/7、5/9 来了三次，左栏就是三条互不相干的记录，
看不出是同一个人，那五行的「历史」也就没有出处。

实测（138 条真会话、112 个不同 `买家昵称`）：

| | |
|---|---|
| 昵称只有一段 | 88 个 |
| 昵称有 2–3 段 | 24 组（共 50 条） |
| 合并后左栏 | 112 个窗口 ＋ 2 条演示线 = **114** |
| 响应体 | 913KB → **876KB**，消息一条没少（1008 条） |
| 装配耗时 | 140 条 3.5ms → 114 条 **4.8ms**（其中合并本身 1.3ms，20 次取最小值） |

**契约变了两个字段**（`schemas.Session`，前端 `types/index.ts` 同一步改）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `以前` | `以前会话[] \| null` | 更早几次来访的总结，时间升序。每行 `{日期, 要什么, 办过什么?, 工单号?}` |
| `起演格` | `int \| null` | 回放从第几格开始 ＝ `以前` 那几段的消息条数之和 |

⚠️ **`以前` 必须是 `[]`，不许是 `null`。** 前端靠它区分两件事：
`undefined`（这一份不是接口给的，两条演示线走 `剧本.ts` 兜底）→ 当老客演，五行正常出；
`[]`（接口明说「这位没有更早的来访」）→ 小卡换成「初次会话」，**五行一条都不渲染**。
写成 `null` 的话两者长得一样，演示两条线的卡片会凭空变成「初次会话」。

> **2026-10-04 更正：这个字段界面上不再渲染了**（原先卡片顶上单有一块
> 「以前来过」）。更早那几次只用来**填那五行**，`以前` 自己只剩一个用途 ——
> 判上面那件事。接口照旧全给：它是契约的一部分，只是暂时没有读者。
> 卡片的另一头是「什么时候从初次会话退出来」（`stage` 写成 `历史联系` 之后），
> 见 `types/index.ts` 的 `会话已结束`。**88 个单段窗口的 `stage` 真数据里没人写**，
> 所以它们就停在「初次会话」那一态。

**窗口 ID 取末段的会话 ID**（`S00034` ＋ `S00132` → 窗口是 `S00132`）——
`装载器.找(会话ID)`、`台账` 的存档键、`动作` 全按会话 ID 索引，取末段就一个
映射都不用加。合并**只在路由层发生**，`装载器` 一行没动：它仍然是 138 条原始
真相，`/healthz` 也照旧报 **140**。两个数不一样是**有意的**。

> ⚠️ **`POST /api/判定` 对合并窗口只能看见末段。** `装.找(会话ID)` 返回的是那条
> 原始会话。今天无害 —— 真窗口走的是「还没跑判定」那条路，按钮根本不显示 ——
> 但接真实判定之前必须先决定「判窗口还是判段」。

**消息序号重编成 1..N。** 原始数据里每个会话各自 1..n（实测 138/138），直接拼
会重号 —— 而 `装配._答应过什么` 正是靠 `sorted(key=消息序号, reverse=True)`
找「最晚一条承诺」，重号之后挑出来的是错的那条。

**顺带修掉一个假逾期。** 合并后 `_答应过什么` 会扫到**前段**客服许下的承诺，
而它原先只拿末段那张票核对，核不上就按「未兑现」算 —— 实测 **3 个**窗口因此
报出**假的**「承诺已逾期」红字（`S00132`／`S00203`／`S00362`：承诺挂的补发单
`补发物流单号` 明明非空、货早发出了），而 `CustomerStateCard` 对带 `警示` 的行
**强制展开**，藏都藏不住。修法是让合并模块产出 `窗口ID → {工单号: 票}`
（那个窗口**所有段**的工单），沿 `_未兑现` → `_答应过什么` → `装配顾客情况`
→ `判定.整会话顾客情况` → 路由**逐层透传**；单段窗口传 `None`，行为逐字不变。

## 二之二 · `POST /api/需求分解`（2026-10-04）

「这次要什么」那一行**不再是把顾客原话攒起来**，改成让模型拆成几条短需求、
用 ` ＋ ` 连起来。接口是这一改的产出者（`api/需求分解.py` ＋ `llm/拆需求.py`）。

### 请求

```json
{ "会话ID": "S_DEMO_A", "看到几句买家话": 2 }
```

| 字段 | 类型 | |
|---|---|---|
| `会话ID` | `str` | 必填。和 `/api/判定` 一样，找不到就 **404**「没有这个会话：X」，不返回空值了事 |
| `看到几句买家话` | `int \| None` | 选填，`ge=0`。**不给 = 整趟都看得见**（真窗口那条路） |

### 响应

```json
{ "会话ID": "S_DEMO_A", "值": "确认精华是否含乙醇 ＋ 补发上次未发赠品" }
```

**`值` 是空串 ＝ 没拆出来**（模型够不着 ／ 答得不成样子 ／ 这一趟她一句买家话
都没有）。这是**正常返回**，不是错误 —— 前端见到空串**什么都不改**，那一行留着
原来那份值。分隔符归后端（`连接符`，和 `装配.这次要什么` 逐字一致），前端一个
字符都不拼。

### 为什么单开一条路，不并进 `/api/会话列表`

那条路一次装配 114 个窗口、纯规则 **18 ms** 出结果。加上模型就是 **114 次调用
排在一个请求里**，而且模型没答上来时它**连原来那份原话都给不出去**（整个响应
就挂了）。所以改成**点开哪个窗口就问哪个**：一次一个请求，延迟落在用户已经点进去
的那一屏上，兜底那份原话早就由列表接口给过了。

### `看到几句买家话` 数的是**买家话**，不是消息条数

这是这条接口最容易接错的一处。两边对同一条会话的编号**对不上**：

- 后端那份 `S_DEMO_A` 多一条**开头**的客服消息（9/25 那条承诺，是补出来的）；
- 剧本那份多一条**现场发**的消息（第 5 格客服点发送出去的那句，后端根本没有）。

所以「第几条消息」在两边指的不是同一句话。**买家话的顺序两边一样**，所以按买家话
切。演示真按消息条数切的话，第 1 格就切到那条承诺上 —— 交出去的是**空的**买家话，
而屏幕上那一行纹丝不动（没拆出来就是留原值），**看不出是切错了**。

### 它还决定「最后一句算不算」

一次来访的最后一句是收场白（实测 24/24），真窗口要看的是她提过的事，不是那句道谢。

| `看到几句买家话` | 末句 |
|---|---|
| 没给，或者给的数**到了末尾** | 这一趟已经过完 → 当成收场白**去掉** |
| 只看到一半 | 会话还在走 → 末句**正是要靠它办事的那句** → 留着 |

两件事其实是同一件事，所以**没有单独的 `已说完` 开关** —— 多一个字段就多一种
「它和它打架」的状态，而那种状态下不会有任何东西报错。去尾那条规矩住在
`装配.本次买家话` 里，路由只是按口径把参数传进去，不在路由里再写一遍。

### 它**不在判定链路上**

`api/判定.py` 那六个模型位它一个都不碰，`判成` 里也没有它（归因是 `拆主张` 的事）。
**产出的是给人看的一行字，没有任何规则读它。** 这句话在 `llm/拆需求.py` 和
`api/需求分解.py` 里各写了一遍，两处都写是因为最容易的坏法是「顺手拿它去判点什么」。

### 和列表那条路必须答**同一个问题**

不传 `看到几句买家话` 时，两条路切的是同一条会话、同一批买家话、同一个「去不去尾」
—— 所以模型答上来的那一次，是**在同一个输入上换了个产出者**，不是「换了个看法」。
对不上的话后果很隐蔽：模型答一句、屏幕换个值，而**没人知道换的是不是同一件事**。
`tests/test_需求分解.py` 里有一条把两边的输入摆在一起核。

> ⚠️ **模型没答上来时屏幕上分不出来。** 演示两条线的剧本值
> （`剧本.ts` 里手写的 `精华含不含乙醇 ＋ 怀孕能不能用`）和模型值长得几乎一样，
> 所以「有没有真跑过」由右栏顶上那行数据源标记说话（`剧本兜底 · 需求分解`）。
> 那条标记**常驻、且不挂在 `import.meta.env.DEV` 后面** —— 演示录的是
> `vite build` 产物，挂 DEV 等于没藏（`PrimerPanel.兜底`）。

## 三 · `POST /api/判定`

### 请求

```json
{ "会话ID": "S00005", "轮次": 2 }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `会话ID` | 是 | |
| `当前时间` | 否 | 省了取服务器时间。**显式传是为了回放** —— 演示时要把「9/26 承诺」那条历史记录当成「现在」重跑一遍 |
| `轮次` | 否 | 省了取最后一轮。补历史轮次是为了让「本轮处置」能逐轮回看 |

**消息不从请求里传**，后端按 `会话ID` 自己查。前端持有完整消息流是个诱惑（它现在就有），
但那样「判定」就不是服务端的事了，留痕也无从记起。

### 响应

| 字段 | 类型 | 说明 |
|---|---|---|
| `会话ID` | `string` | |
| `轮次` | `number` | |
| `顾客情况` | `StateRow[]` | 固定五行，顺序不能改 |
| `安全事件` | `安全事件条目[]` | 输入安全层（注入／违规／PII／辱骂） |
| `触发` | `触发条目[]` | 命中的硬触发 H1–H4 |
| `本轮处置` | `Disposition[]` | 一条主张一条 |
| `主卡` | `Advice \| null` | `null` = 本轮没有要客服动手的事 |
| `闸门` | `闸门命中[]` | 被 G1–G4 拦下的记录 |

### 出错时

两类错收敛成同一个形状（`main.py:装异常处理`），前端**一个分支**就够：

```json
{ "错误": "没有这个会话：S_不存在", "详情": "" }
```

| 状态码 | 什么时候 | `错误` |
|---|---|---|
| `404` | `会话ID` 在装载器里查不到 | `没有这个会话：<ID>` |
| `422` | 请求体缺字段／类型不对 | `请求参数不合法`，细节在 `详情` |

`详情` 是排障用的（422 时是 pydantic 的 `loc: msg` 压成一行），前端可以只显示
`错误`。FastAPI 默认给的是 `{"detail": …}`，而校验错给的是 `{"detail": [...]}`
—— 同一个键名两种类型，前端要写两个分支去取，而界面上只有一个地方显示错误，
**第二个分支永远不会被写**，出错时界面上什么都不显示。

## 三之二 · 四个按钮的三个接口（2026-10-03 落地 · `api/动作.py`）

### 三个路由都要求先打一次 `/api/判定`

`报备`／`转交` 的七行里有四行是**上一跳判出来的**（诉求、升级分类、承诺与逾期），
`发送` 收到的 `采用的处置id[]`（`S_DEMO_A-2-1` 这种）更是**只有服务端那张
id → 主张 的表才认得** —— 没有它，这串 id 就是一堆没人认得的字符串。

所以 `判定` 把这一轮的产物往 `api/台账.py` 里写一份（进程内、不落盘），
三个动作接口读它。**没判过 → 409，不是空单子**：空单子在界面上是「七行全是
「—」」，看着像数据缺失，而真正的原因是这个会话还没判过。

> 台账存的 `当前` 是**判定那一刻的「现在」**，不是 `date.today()`：
> 单号的日期取它。演示的今天是 2026-09-29，录制却在别的日子，取真实时钟的话
> 屏幕上会出现「9/29 已逾期 2 天」和一张 `JJ20261003…` 的单子并排。

### 报备／转交

```json
// 请求 —— 两个接口同一个形状，只有一个字段
{ "轮次": 2 }
```

**`轮次` 必填，不给就 422。** 它防的是「**有一张、但属于另一轮**」：台账一个
会话只留**最后那一轮**判定（后判的盖掉先判的），而前端是按轮显示的 ——
演到第 7 步（轮次 2）再拖回第 4 步（轮次 1），屏幕上是轮次 1 的内容，不带轮次
的话后端会照着轮次 2 立一张单子，**而那张单子看着完全正常**（七行都有、单号也在）。
带上轮次对不上一记 409，右栏把后端那句话原样摆出来。

> ⚠️ **这一格 2026-10-03 才加**（`工单交接_给接口线_C.md` §二 拍的甲）。在那之前
> 两个接口**没有请求体**，后端只能拿台账里最后那一轮 —— 上面那个安静的错误就是
> 那时候的常态。前端那个「当前轮次」只对有剧本的会话有值，138 条真会话没有轮次，
> 但它们现在压根不显示动作按钮（`未判定` 那条路），所以不冲突；
> **接真会话判定之前要回来看一眼这里。**

两个都回**同一个形状** `交接包`：

```json
{
  "状态": "等待审批",
  "行": [{ "标签": "工单类型", "值": "补发工单（赠品漏发）", "来源": "会话.工单.kind ＋ 本轮处置（转交取 H1 命中词，报备取主张）" }],
  "单号": "JJ20260929001"
}
```

| 字段 | 值域 | 谁定 |
|---|---|---|
| `状态` | `等待审批`（报备）／`已转出`（转交）／`已完成` | 报备／转交那一刻定下前两个（写死）；`已完成` **由 `发送` 推**，见下面「已完成那一格」 |
| `行` | **七行，顺序固定** | 顺序就是 `31 §3.6` 那张表的行序，右栏照着渲染 —— 调顺序等于改界面 |
| `单号` | `JJ{YYYYMMDD}{序号:03d}` | 后端出。见下面 §五 那条去重 |

**`等待审批` 不是「组长还没批」，是「**这一单还没走完**」。** 第 8 步（组长批准了、
话还没发）的徽标也显示它 —— 那一格**没有事件源**（系统里没有任何东西产出「批准」
这件事，只有剧本知道），而 `31 §1.4` 只列了 `等待审批 · 已完成` 两个值，不为它
单开一格（2026-10-03 拍板：加第四个值的方案被否了，见 `工单交接_给接口线_C.md` §一 1.3）。

#### 「已完成」那一格

报备单生命周期上三个事件，只有两个有源：

| 事件 | 谁产出 |
|---|---|
| 交上去了 | ✅ 客服点那一下（`POST …/报备`） |
| 组长批准了 | ❌ **系统里没有任何东西产出它** —— 只有剧本知道（第 8 步那格） |
| 答复完了 | ✅ **前后端都知道** —— 客服点了［一键发送］／［发送］，`台账.记发送` 落了痕 |

所以 `已完成` 是**「答复完了」**推出来的，不需要发明事件：`发送` 落完留痕之后
把这一会话那张报备单推到 `已完成`，响应里带出来（`报备单态`，见下一节），
前端跟着改 `交接包表`。`状态` 仍然是**后端一个真源**，前端只搬不判。

⚠️ **判据是「这个会话有一张报备单，且它答复出去了」，不是「发送过就完成」。**
两条理由：`台账.记发送` 是**追加**的（一轮可以发好几条）；而 `发送` 也被
「客服点发送」那一支用 —— 那一支**根本没有报备单**，照「发送过」判会把一堆
没报备过的会话标成已完成。转交过的也不推（`已转出` 是终点，转交压根不记报备单）。

**⚠️ 报备也回七行，这是对本文档上一版的有意偏离。** 上一版把这一行写成
「生成工单号」，只有 `转交` 写「交接包（7 行 ＋ 单号）」。可 `31 §3.6` 的
**顾客 A 那一列就是报备那一列**（S10 演的是［一键报备］），七行一行不少 ——
两边同形，前端那个 `建交接包()` 才能**整块**删掉。

> ⚠️ **2026-10-03 更正：「才能整块删掉」这一句没照办，是拍过的。** 前端接上之后
> **`建交接包()` 留作兜底没删**（`工单交接_给前端线_B.md` §一 1.1 拍的是**乙**）——
> 判定的兜底是 `剧本.ts` 那份已知正确的数据，交接包没有对应的那一份，删了它
> 后端一挂［一键报备］点下去右栏**安静地少一块**。上一条的前提（两边同形）仍然成立，
> **不成立的是那个结论**。
>
> 那条尾巴（`状态` 永远停在 `等待审批`）**2026-10-03 修了** —— 见上面
> 「已完成那一格」（`工单交接_给接口线_C.md` §一 走的甲）。

**行 1／行 3／行 7 的措辞跟现场走，不是固定字面。** 这三行的值来自本轮真实
判出来的主张（`拆主张` 是模型），而模型**不照着清单上的字说** —— 2026-10-03
真跑那两条线，模型给的是「赠品尚未发出」（清单上写的是「赠品漏发」），B 那轮
甚至拆出 **4 条**主张。所以 `31 §3.6` 是**形状基准**，不是逐字台词。

### 发送

```json
// 请求
{ "轮次": 2,
  "话术": "亲实在抱歉让您久等，赠品的事我立刻帮您核实，尽快答复您～",
  "采用的处置id": ["S_DEMO_A-2-1"] }

// 响应
{ "会话ID": "S_DEMO_A", "轮次": 2,
  "话术": "亲实在抱歉让您久等，……",
  "兑现主张": ["赠品尚未发出"],
  "报备单态": "已完成" }
```

`轮次` 和另两个接口同一个理由（见上一节），**同样必填**。这里多一层：轮次整条
对不上时，客服手上那几个处置 id 属于**另一轮** —— 后端拿自己那一轮的表去比，
命中的话就记成了一条发生在别的轮次上的留痕。所以轮次校验在 id 校验**之前**。

`采用的处置id[]` 存在的**唯一理由**就是 `兑现主张`：客服点［采用］再点［发送］，
这一句对应哪几条主张要记下来，留痕回放时「这条诉求办没办」全靠它。后端
按请求里给的**顺序**回，不乱排。

**空数组是合法的**：客服自己敲一句话直接发是常态，如实回 `[]` ——
不许拿「本轮最高态」替客服认领几条主张，那会让留痕记下一件没发生过的事。

`报备单态` 是**这句话发出去之后**那张报备单的状态（`已完成`），见上面
「已完成那一格」。⚠️ **`null` 不等于「没推进」**，它是「**这个会话没有这张
单子**」：没报备过的（普通会话、客服自己敲一句直接发）、转交过的、以及请求的
轮次和立单那一轮对不上的，都回 `null`。**前端只在非 `null` 时才去改那张单子**——
把 `null` 当成 `已完成` 的话，客服随便回一句话，右栏就会冒出一张从来没报备过的
「已完成」交接包。

**这个接口不查禁语、不查事实。** 那两道在本地（见 §二 那条）。

### 出错时

| 码 | 什么时候 | 为什么不静默 |
|---|---|---|
| `404` | 会话不存在 | 和 `/api/判定` 一样：**空结果和没结果是两件事**，界面上长得一样，排查方向却相反 |
| `409` | 这个会话还没判定过 | 空交接包会伪装成「数据缺失」 |
| `409` | **请求的轮次和台账里那一轮对不上** | 这是安静的那一种：后端照样能照最后判的那一轮立一张单子，**而那张单子看着完全正常**。`detail` 把两边轮次都写出来（「你点的是第 1 轮，台账里是第 2 轮」） |
| `409` | **这一轮**没有要走这条去向的主张（拿 A 第 3 轮「道谢」点报备） | 拿别的去向顶替的话，屏幕上那张单子会**静默变成上一轮**的，而看着一切正常 |
| `400` | `采用的处置id[]` 里有不在本轮的 id | 静默丢掉的话，这一句在留痕里变成「一条主张都没兑现」，和「客服确实什么都没兑现」长得一模一样 |
| `422` | 请求没带 `轮次` | 必填。**可选的话就留了个安静的口子**：漏传一个字段，后端退回「拿最后那一轮」那套老行为，而屏幕上根本看不出点的是哪一轮 |

⚠️ 上面两个 `409` 说的**不是一回事**，`detail` 也得说得出区别 —— 否则排障时会
把「这一轮没东西可报」和「你点的那一轮不是后端手上这一轮」当成同一件事。

形状仍是 `{"错误": …, "详情": …}`（`main.py` 那两个字处理函数）。

## 四 · 两处刻意的偏离

契约和 `docs/开发步骤.md` 的样例有两处不一样，都是想清楚了的。

### 1 · `已代发` 只在 `主卡` 里，顶层没有

开发步骤 的样例响应顶层也写了一个 `已代发`。**那是同一份数据传两遍** ——
两份一旦不同步，右栏两处会显示不一样的内容，而**两处都看着对**。
前端只在 `Advice` 里读它，所以顶层那个删掉。

### 2 · `草稿` 不进后端

前端 `Session` 有 16 个字段，`schemas.Session` 有 15 个，缺的是 `草稿`。

**`草稿` 是输入框里的字** —— 客服正在敲、随时在变的东西。前端自己的注释写着
「输入框内容随时会变，禁语必须在每次编辑后用 `查禁语()` 重新比对」。
后端声明一个 `草稿` 等于声称自己管着一份它看不见的副本。

代价是「每个字段逐字对应」这句话字面上不成立，所以 `test_schemas.py` 里为它留了
一条**写明理由**的例外（断言差集**恰好**是 `{草稿}`），而不是硬塞个字段让断言好看。

### 附 · 两个提成命名模型的内联结构

前端把 `报备?: { 等待分钟: number; 工单号: string }` 和 `转交?: { 工单号: string }`
**内联**写在 `Session` 里。后端给它们起了名字（`报备状态` / `转交状态`）——
**线上形状完全一致**，只是出现两次以上的结构给个名字，文档和留痕都要引用。
字段名测试按形状核对，不受影响。

## 五 · 证据进线上形状的映射 —— `api/证据.py`

规则层查出来的是 `sources.源记录`（v9 §4.1 的 `{exists, table, row_id, content}`），
线上要的是 `Evidence`。字段名是英文对中文，**这层转换是唯一一处真正的映射**，
放在接口层（`api/证据.py`），别扩散到别处。

### 先把三个名字对齐

| 名字 | 住在哪 | 有什么 |
|---|---|---|
| `sources.源记录` | 规则层 | `exists` / `table` / `row_id` / `content` / `用上` |
| `guards.依据条目` | 规则层下游 | `序号` / `出处` / `摘要` / `用上` / `成分` |
| `schemas.Evidence` | 线上形状 | `序号` / `出处` / `摘要` / `用上` |

⚠️ **`工单 §五` 那张表的表头写「`源记录` → `Evidence`」，表里的字段却是
`依据条目` 的。** 两者对不上，而且**都对不上对方**：

- `源记录` **没有 `序号`** —— 序号是 `六源结果.记录` 那个 dict 的**键**。
  拿到一批 `源记录` 时序号已经丢了。
- `依据条目` **没有 `table` / `row_id`** —— 它在链路更下游，出处早拼成
  「口径表 K05「赠品补发承诺」」这样的整句了。

### 所以实现是两个函数，不是一个

| 函数 | 收 | 谁在用 |
|---|---|---|
| `证据.从六源(六源结果)` | `sources.六源结果` | ✅ `Advice.依据` —— 主卡那份六源清单 |
| `证据.从依据条目(条目们)` | `guards.依据条目` | ✅ `已代发[].依据` —— **这一句**话引的那几条 |

硬凑成一个的话，要么六源那边丢了出处，要么对着 `源记录` 找 `序号` 当场
`AttributeError`。

**两条边喂的是右栏里两块不同的地方**，别「统一下来」：换成 `从六源` 的话，
那句「亲，这款不含乙醇哦～」下面会挂着整轮查到的六源（包括孕妇那条的 K01）；
换成 `从依据条目` 的话，主卡那份清单会丢掉没被引用的来源，
`N/6 源命中` 的分母就从 6 变成「引了几源」—— **两处都看着对**。

### `源记录` 的字段怎么落到 `Evidence` 上

| `源记录` | `Evidence` | 怎么来 |
|---|---|---|
| （所在键） | `序号` | `六源结果.记录` 的**键**。①②③④⑤⑥，封闭集合 |
| `table` ＋ `row_id` | `出处` | 拼成 `「口径表 K05」`。**只拼接，不美化** |
| `content` | `摘要` | 原样。太长就截断，**截断要说**（上限 60 字，超了补 `…`） |
| `用上` | `用上` | **两套取值，见下** |

`从六源` **只放 `exists=True` 的**，没查到的由前端按六源补空位（下面那条）。
`用上=False` 的**要出** —— 它进「未命中的六源清单」，带着摘要一并列。
`exists` 和 `用上` 问的是两件事：查到但没引用，第 1 层仍算「查得到」，
只是 `N/6 源命中` 不算它。

`从依据条目` 里 **`成分` 丢掉**：它是 G3 的输入，对客服没有意义，
而且 `Evidence` 压根没这个字段 —— 不是「记得别传」，是没有传的路径。

### `用上` 取哪一边：两套取值，按主张分（spec §6.4）

`源记录.用上` 在检索层**恒为 `True`**（`六源.py` 的文件头：出去的每一条都是
`exists=True`、`用上=True`），照搬的话 `用上` 就是个常量 —— 右栏 `N/6 源命中`
恒等于「查到了几源」，展开后那段「未命中的六源清单」恒为空。
**「查到」和「引用」被一个常量合并成了一个词**，而两处都看着对。

所以 `判定` 按主张分两种（`_自报映射` 出「谁自报过」，`_用上按自报` 逐条压）：

| 主张 | `用上` 取 | 为什么 |
|---|---|---|
| 走过 3c（`AI直发`／`客服点发送`） | `生成结果.用到的依据`（**模型自报**） | 右栏问的是「这句话引了哪几条」 |
| 没走 3c（`报备`／`转交`） | 检索层原值（恒 `True`） | 那两条话术走固定表、压根没进模型，没有自报可取。而那个 `True` 是**诚实的**：报备那三条硬边界是照 ⑥ 工单写的，依据确实用上了，只是用的人不是模型 |

**`Advice.依据` 和 `已代发[].依据` 都走这一套**，用的是同一对函数
（`判定._自报映射` / `_用上按自报`）。所以同一个 `出处` 在两张表里
`用上` 必然一致 —— 哪个都别单独改成常量：`已代发` 那条曾经直接搬
`源记录.用上`，于是「亲，这款不含乙醇哦～」下面挂着 `② 口径表 K10 用上=true`，
而主卡清单里同一行是 `false`，**同一份数据在同一屏上自相矛盾**。

⚠️ `_自报映射` 里「**这条主张不在表里**」（没走 3c）和「**在表里但是空集**」
（走了 3c 却一条都没自报）是**两件事**，前者回落检索层、后者如实报 `false`。
用 `dict.get(主张, ())` 一把兜住的话，没走 3c 的那条会被压成 `false`。

⚠️ **别「一刀切取模型自报」**：`报备` 那条没自报，一刀切会把整轮依据压成
`False`，`N/6` 变 `0/6` 并宣称「另 6 源无记录」—— 而 ⑥ 工单是查到了的。

⚠️ 模型自报的出处抄的是 prompt，拼法是 `「口径表 · K10」`（`依据条目` 那种），
而 `Evidence.出处` 是 `「口径表 K10」`（`证据._出处`，只拼接不美化）。
**整串相等一条都命不中**，所以比对前两边都过一遍 `判定._出处键`（去掉空格和 `·`）。
漏掉这步的后果不是报错，是每一条都变成「没用上」。

### `依据` 的两条规矩（开发步骤 明写，这里定死）

**1 · 一个来源可以有多条引用，别按来源去重。**

口径表同时命中 K06「不良反应处理」和 K20「投诉与升级」是正常的 ——
两条都要返回、都要显示。同一个「赠品漏发」也可能既认到 K07 又认到 K05。
**计数时才按来源折算**（`N/6 源命中` 里的 N），列出来的时候一条都不能少。

**2 · 后端只返回查到的，前端按六源补空位。**

`exists=True` 的那些才有对应的 `源记录`，`Advice.依据` 只放这些。
没查到的五个来源由前端补成 `用上: false` 的空位（样例里 ①③⑤ 三行就是）。

这样 `N/6 源命中` 和「另 N 源无记录」在任何后端实现下都成立，也不会漏列 ——
后端不需要知道前端要补几个空位。

### 那条「没有遗漏」的承诺，粒度说清楚

- **做得到 —— 在「六个来源」这个粒度上。** 六源是封闭集合，逐个报
  「有记录／无记录」可穷举。所以 `Evidence.序号` 的类型是 `六源` 而不是 `str`：
  声明成 `str`，第 7 个来源会以字符串的形式悄悄溜进右栏。
- **做不到 —— 源内没有截断。** ① 商品属性表和 ③ 先例库内部走向量召回，
  天然是 top-K。「① 查过了」不等于「① 里每一行都看过了」。演示时主动说这一层限度。

## 六 · `闸门命中` 和 `GuardHit` 不是一回事

两个名字像、用途不同，**别合并**：

| | `GuardHit` | `闸门命中` |
|---|---|---|
| 管什么 | 口径表禁语（K01–K20） | G1–G4 四道闸门 |
| 回答什么 | 「这句话能不能发」 | 「AI 为什么没发出去」 |
| 用在哪 | 输入框下面那条红提示；步骤 4 的 `POST /草稿检查` | `POST /api/判定` 的 `闸门` |
| 字段数 | 3 | 8 |

合并会丢掉 `可重生成` 和 `降级去向` —— 而 `降级去向` 是 **G3 唯一的载体**。
v9 §五 G3 的去向是「不许自动发，**降为客服点发送**」：话术本身没问题，
是我们对它的来源没把握。这个字段没了，前端只能说「被拦了」，说不出「拦完改判成什么」。

**`可重生成` 和 `降级去向` 问的不是一回事**，别混：
前者是「这句话还能不能救」，后者是「就算救活了也不许自动发」。

## 八 · 改契约要动哪几个文件

| 改什么 | 动哪儿 |
|---|---|
| 加/删/改一个字段 | `types/index.ts` **和** `schemas.py` 两处一起；`test_schemas.py` 会红到你改齐 |
| 加一个枚举取值 | 先改枚举，前端联合类型跟着改（改哪一处见下） |
| 改一个字段的类型 | 同上，外加本文档的字段表 |
| 改 `StateRow` 的结构 | 同上三处。**2026-10-01 已定要改**：`这次要什么` 由单值改多值（按事实点），见 §七 第 3 条 |

**「先改枚举」的「哪一处」要看是哪个枚举**，不是一律在 `app/rules/`：

| 枚举 | 住在哪 | 为什么 |
|---|---|---|
| `输出类型` `类别` `处置` `触发编号` `六源` | `app/rules/` | 规则层自己要用，线上形状是它的投影 |
| `SenderRole` `ContentType` `SessionStage` `TicketKind` | `schemas.py` | **规则层不碰它们** —— 它们是会话数据的形状，只在这一层有定义 |

在 `schemas.py` 里就是源头，测试只能比值（TS 联合 vs Python 的字面量）。
