# 接口契约

「一句话进来 → 右栏出什么」的 JSON 形状。

**代码是 `backend/app/api/schemas.py`，这份文档给它配人话。** 两边说的是一件事，
不一致时以 `schemas.py` 为准 —— 它有测试跟着跑，文档没有。

> 本文里那个样例 JSON 是**测试真的会去解析**的
> （`tests/test_schemas.py::test_接口契约文档里的样例能通过校验`）。
> 随手改一改字段名不会有人发现，但改坏形状会当场变红。

---

## 一 · 三条规矩

**1 · 字段名逐字照 `frontend/src/types/index.ts`，两边一字不差。**

中文名、大小写、可选性全照抄，**不引入映射层** —— 后端叫什么，线上就叫什么。
这是 `docs/开发步骤.md` 步骤 0 的完成标准，由 `tests/test_schemas.py` 逐字段核对：
它**真的去解析那个 TS 文件**，不是在这儿手抄一份再跟自己比。

为什么值得专门修一道防线：两边字段名漂移**不会让任何东西报错**。后端多拼一个字、
前端读 `undefined`，界面只是少显示一块 —— 直到演示当天有人问「这儿怎么是空的」。
这是唯一一类「两边都编译得过、两边都测试通过、合起来却是坏的」的错。

**2 · 枚举从 `app/rules/` import，不另抄一份。**

`输出类型` / `类别` / `处置` / `触发编号` / `六源` 都有现成的 —— 这五个
`schemas.py` 直接从 `app/rules/` import（`schemas.py:34-37`），测试用 `is` 断言
「就是规则层那个对象本身」，专拦「抄了一份、恰好值一样」。

⚠️ **`权限去向` 不在这一组里**，别照抄这句话去 import 它 —— `schemas.py:218`
声明的是 `str`，值域靠字样对齐（见 `app/rules/permissions.py`），没有 `is` 断言。
这是**有意的取舍**：它是个开放集合，加一个去向不该要动三个文件。

**3 · 别名只在 Python 语法不允许时用。**

四个带括号的金额列（`单价(元)`、`实付金额(元)`、`退款金额(元)`、`订单实付(元)`）
不是合法的 Python 标识符，只能换个属性名再挂 `alias=`。

**这不是映射层** —— 线上跑出来的键就是 `单价(元)`，和前端一模一样。
`契约模型` 上设了 `serialize_by_alias=True`，所以不带参数调 `model_dump()`
也走别名。这一条是防一个具体的坑：默认走属性名的话，前端读到 `undefined`
**而且不报错**，界面上只是少了一个数字。

## 二 · 接口清单

| 方法 | 路径 | 干什么 | 步骤 | 建了吗 |
|---|---|---|---|---|
| `GET` | `/healthz` | 活着没 | 1 | ✅ |
| `GET` | `/api/会话列表` | 左侧列表 ＋ 中部聊天区的全部数据 | 1 | ✅ |
| `POST` | `/api/判定` | 一句话进来 → 右栏出什么 | 2 | ✅ 2026-10-01 · `api/判定.py` |
| `POST` | `/api/草稿检查` | 输入框每次编辑后的禁语比对 | 4 | ❌ |
| `POST` | `/api/报备` `POST /api/转交` `POST /api/发送` | 客服动手的三个动作 | 4 | ❌ |

**步骤 0 只定形状，不写路由。** 这张表列出来，是为了让人看清 `判定请求`
在整条链的哪一环 —— 它前面是数据装载（步骤 1），后面才是客服动手（步骤 4）。

前三条已经能打（`路由.py` 管前两条，`判定.py` 管 `POST /api/判定`），
**后三条一行都还没写**。所以今天的演示是**只读的**：右栏能出东西，
但「报备」「转交」「发送」三个按钮打不到任何后端 ——
别把「接口通了」理解成「整条链通了」。

## 三 · `POST /api/判定`

### 请求

```json
{ "会话ID": "S00005", "轮次": 2 }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `会话ID` | 是 | |
| `当前时间` | 否 | 省了取服务器时间。**显式传是为了回放** —— 演示时要把「9/26 承诺」那条历史记录当成「现在」重跑一遍 |
| `轮次` | 否 | 省了取最后一轮。补历史轮次是为了让「本轮处置」能逐轮回看 |

**消息不从请求里传**，后端按 `会话ID` 自己查。前端持有完整消息流是个诱惑（它现在就有），
但那样「判定」就不是服务端的事了，留痕也无从记起。

### 响应

| 字段 | 类型 | 说明 |
|---|---|---|
| `会话ID` | `string` | |
| `轮次` | `number` | |
| `顾客情况` | `StateRow[]` | 固定五行，顺序不能改 |
| `安全事件` | `安全事件条目[]` | 输入安全层（注入／违规／PII／辱骂） |
| `触发` | `触发条目[]` | 命中的硬触发 H1–H4 |
| `本轮处置` | `Disposition[]` | 一条主张一条 |
| `主卡` | `Advice \| null` | `null` = 本轮没有要客服动手的事 |
| `闸门` | `闸门命中[]` | 被 G1–G4 拦下的记录 |

### 出错时

两类错收敛成同一个形状（`main.py:装异常处理`），前端**一个分支**就够：

```json
{ "错误": "没有这个会话：S_不存在", "详情": "" }
```

| 状态码 | 什么时候 | `错误` |
|---|---|---|
| `404` | `会话ID` 在装载器里查不到 | `没有这个会话：<ID>` |
| `422` | 请求体缺字段／类型不对 | `请求参数不合法`，细节在 `详情` |

`详情` 是排障用的（422 时是 pydantic 的 `loc: msg` 压成一行），前端可以只显示
`错误`。FastAPI 默认给的是 `{"detail": …}`，而校验错给的是 `{"detail": [...]}`
—— 同一个键名两种类型，前端要写两个分支去取，而界面上只有一个地方显示错误，
**第二个分支永远不会被写**，出错时界面上什么都不显示。

## 四 · 两处刻意的偏离

契约和 `docs/开发步骤.md` 的样例有两处不一样，都是想清楚了的。

### 1 · `已代发` 只在 `主卡` 里，顶层没有

开发步骤 的样例响应顶层也写了一个 `已代发`。**那是同一份数据传两遍** ——
两份一旦不同步，右栏两处会显示不一样的内容，而**两处都看着对**。
前端只在 `Advice` 里读它，所以顶层那个删掉。

### 2 · `草稿` 不进后端

前端 `Session` 有 16 个字段，`schemas.Session` 有 15 个，缺的是 `草稿`。

**`草稿` 是输入框里的字** —— 客服正在敲、随时在变的东西。前端自己的注释写着
「输入框内容随时会变，禁语必须在每次编辑后用 `查禁语()` 重新比对」。
后端声明一个 `草稿` 等于声称自己管着一份它看不见的副本。

代价是「每个字段逐字对应」这句话字面上不成立，所以 `test_schemas.py` 里为它留了
一条**写明理由**的例外（断言差集**恰好**是 `{草稿}`），而不是硬塞个字段让断言好看。

### 附 · 两个提成命名模型的内联结构

前端把 `报备?: { 等待分钟: number; 工单号: string }` 和 `转交?: { 工单号: string }`
**内联**写在 `Session` 里。后端给它们起了名字（`报备状态` / `转交状态`）——
**线上形状完全一致**，只是出现两次以上的结构给个名字，文档和留痕都要引用。
字段名测试按形状核对，不受影响。

## 五 · 证据进线上形状的映射 —— `api/证据.py`

规则层查出来的是 `sources.源记录`（v9 §4.1 的 `{exists, table, row_id, content}`），
线上要的是 `Evidence`。字段名是英文对中文，**这层转换是唯一一处真正的映射**，
放在接口层（`api/证据.py`），别扩散到别处。

### 先把三个名字对齐

| 名字 | 住在哪 | 有什么 |
|---|---|---|
| `sources.源记录` | 规则层 | `exists` / `table` / `row_id` / `content` / `用上` |
| `guards.依据条目` | 规则层下游 | `序号` / `出处` / `摘要` / `用上` / `成分` |
| `schemas.Evidence` | 线上形状 | `序号` / `出处` / `摘要` / `用上` |

⚠️ **`工单 §五` 那张表的表头写「`源记录` → `Evidence`」，表里的字段却是
`依据条目` 的。** 两者对不上，而且**都对不上对方**：

- `源记录` **没有 `序号`** —— 序号是 `六源结果.记录` 那个 dict 的**键**。
  拿到一批 `源记录` 时序号已经丢了。
- `依据条目` **没有 `table` / `row_id`** —— 它在链路更下游，出处早拼成
  「口径表 K05「赠品补发承诺」」这样的整句了。

### 所以实现是两个函数，不是一个

| 函数 | 收 | 谁在用 |
|---|---|---|
| `证据.从六源(六源结果)` | `sources.六源结果` | ✅ `Advice.依据` —— 主卡那份六源清单 |
| `证据.从依据条目(条目们)` | `guards.依据条目` | ✅ `已代发[].依据` —— **这一句**话引的那几条 |

硬凑成一个的话，要么六源那边丢了出处，要么对着 `源记录` 找 `序号` 当场
`AttributeError`。

**两条边喂的是右栏里两块不同的地方**，别「统一下来」：换成 `从六源` 的话，
那句「亲，这款不含乙醇哦～」下面会挂着整轮查到的六源（包括孕妇那条的 K01）；
换成 `从依据条目` 的话，主卡那份清单会丢掉没被引用的来源，
`N/6 源命中` 的分母就从 6 变成「引了几源」—— **两处都看着对**。

### `源记录` 的字段怎么落到 `Evidence` 上

| `源记录` | `Evidence` | 怎么来 |
|---|---|---|
| （所在键） | `序号` | `六源结果.记录` 的**键**。①②③④⑤⑥，封闭集合 |
| `table` ＋ `row_id` | `出处` | 拼成 `「口径表 K05」`。**只拼接，不美化** |
| `content` | `摘要` | 原样。太长就截断，**截断要说**（上限 60 字，超了补 `…`） |
| `用上` | `用上` | **两套取值，见下** |

`从六源` **只放 `exists=True` 的**，没查到的由前端按六源补空位（下面那条）。
`用上=False` 的**要出** —— 它进「未命中的六源清单」，带着摘要一并列。
`exists` 和 `用上` 问的是两件事：查到但没引用，第 1 层仍算「查得到」，
只是 `N/6 源命中` 不算它。

`从依据条目` 里 **`成分` 丢掉**：它是 G3 的输入，对客服没有意义，
而且 `Evidence` 压根没这个字段 —— 不是「记得别传」，是没有传的路径。

### `用上` 取哪一边：两套取值，按主张分（spec §6.4）

`源记录.用上` 在检索层**恒为 `True`**（`六源.py` 的文件头：出去的每一条都是
`exists=True`、`用上=True`），照搬的话 `用上` 就是个常量 —— 右栏 `N/6 源命中`
恒等于「查到了几源」，展开后那段「未命中的六源清单」恒为空。
**「查到」和「引用」被一个常量合并成了一个词**，而两处都看着对。

所以 `判定` 按主张分两种（`_自报映射` 出「谁自报过」，`_用上按自报` 逐条压）：

| 主张 | `用上` 取 | 为什么 |
|---|---|---|
| 走过 3c（`AI直发`／`客服点发送`） | `生成结果.用到的依据`（**模型自报**） | 右栏问的是「这句话引了哪几条」 |
| 没走 3c（`报备`／`转交`） | 检索层原值（恒 `True`） | 那两条话术走固定表、压根没进模型，没有自报可取。而那个 `True` 是**诚实的**：报备那三条硬边界是照 ⑥ 工单写的，依据确实用上了，只是用的人不是模型 |

**`Advice.依据` 和 `已代发[].依据` 都走这一套**，用的是同一对函数
（`判定._自报映射` / `_用上按自报`）。所以同一个 `出处` 在两张表里
`用上` 必然一致 —— 哪个都别单独改成常量：`已代发` 那条曾经直接搬
`源记录.用上`，于是「亲，这款不含乙醇哦～」下面挂着 `② 口径表 K10 用上=true`，
而主卡清单里同一行是 `false`，**同一份数据在同一屏上自相矛盾**。

⚠️ `_自报映射` 里「**这条主张不在表里**」（没走 3c）和「**在表里但是空集**」
（走了 3c 却一条都没自报）是**两件事**，前者回落检索层、后者如实报 `false`。
用 `dict.get(主张, ())` 一把兜住的话，没走 3c 的那条会被压成 `false`。

⚠️ **别「一刀切取模型自报」**：`报备` 那条没自报，一刀切会把整轮依据压成
`False`，`N/6` 变 `0/6` 并宣称「另 6 源无记录」—— 而 ⑥ 工单是查到了的。

⚠️ 模型自报的出处抄的是 prompt，拼法是 `「口径表 · K10」`（`依据条目` 那种），
而 `Evidence.出处` 是 `「口径表 K10」`（`证据._出处`，只拼接不美化）。
**整串相等一条都命不中**，所以比对前两边都过一遍 `判定._出处键`（去掉空格和 `·`）。
漏掉这步的后果不是报错，是每一条都变成「没用上」。

### `依据` 的两条规矩（开发步骤 明写，这里定死）

**1 · 一个来源可以有多条引用，别按来源去重。**

口径表同时命中 K06「不良反应处理」和 K20「投诉与升级」是正常的 ——
两条都要返回、都要显示。同一个「赠品漏发」也可能既认到 K07 又认到 K05。
**计数时才按来源折算**（`N/6 源命中` 里的 N），列出来的时候一条都不能少。

**2 · 后端只返回查到的，前端按六源补空位。**

`exists=True` 的那些才有对应的 `源记录`，`Advice.依据` 只放这些。
没查到的五个来源由前端补成 `用上: false` 的空位（样例里 ①③⑤ 三行就是）。

这样 `N/6 源命中` 和「另 N 源无记录」在任何后端实现下都成立，也不会漏列 ——
后端不需要知道前端要补几个空位。

### 那条「没有遗漏」的承诺，粒度说清楚

- **做得到 —— 在「六个来源」这个粒度上。** 六源是封闭集合，逐个报
  「有记录／无记录」可穷举。所以 `Evidence.序号` 的类型是 `六源` 而不是 `str`：
  声明成 `str`，第 7 个来源会以字符串的形式悄悄溜进右栏。
- **做不到 —— 源内没有截断。** ① 商品属性表和 ③ 先例库内部走向量召回，
  天然是 top-K。「① 查过了」不等于「① 里每一行都看过了」。演示时主动说这一层限度。

## 六 · `闸门命中` 和 `GuardHit` 不是一回事

两个名字像、用途不同，**别合并**：

| | `GuardHit` | `闸门命中` |
|---|---|---|
| 管什么 | 口径表禁语（K01–K20） | G1–G4 四道闸门 |
| 回答什么 | 「这句话能不能发」 | 「AI 为什么没发出去」 |
| 用在哪 | 输入框下面那条红提示；步骤 4 的 `POST /草稿检查` | `POST /api/判定` 的 `闸门` |
| 字段数 | 3 | 8 |

合并会丢掉 `可重生成` 和 `降级去向` —— 而 `降级去向` 是 **G3 唯一的载体**。
v9 §五 G3 的去向是「不许自动发，**降为客服点发送**」：话术本身没问题，
是我们对它的来源没把握。这个字段没了，前端只能说「被拦了」，说不出「拦完改判成什么」。

**`可重生成` 和 `降级去向` 问的不是一回事**，别混：
前者是「这句话还能不能救」，后者是「就算救活了也不许自动发」。

## 八 · 改契约要动哪几个文件

| 改什么 | 动哪儿 |
|---|---|
| 加/删/改一个字段 | `types/index.ts` **和** `schemas.py` 两处一起；`test_schemas.py` 会红到你改齐 |
| 加一个枚举取值 | 先改枚举，前端联合类型跟着改（改哪一处见下） |
| 改一个字段的类型 | 同上，外加本文档的字段表 |
| 改 `StateRow` 的结构 | 同上三处。**2026-10-01 已定要改**：`这次要什么` 由单值改多值（按事实点），见 §七 第 3 条 |

**「先改枚举」的「哪一处」要看是哪个枚举**，不是一律在 `app/rules/`：

| 枚举 | 住在哪 | 为什么 |
|---|---|---|
| `输出类型` `类别` `处置` `触发编号` `六源` | `app/rules/` | 规则层自己要用，线上形状是它的投影 |
| `SenderRole` `ContentType` `SessionStage` `TicketKind` | `schemas.py` | **规则层不碰它们** —— 它们是会话数据的形状，只在这一层有定义 |

前者那一组，`test_schemas.py` 用 `is` 断言「就是规则层那个对象本身」；后者那一组
在 `schemas.py` 里就是源头，测试只能比值（TS 联合 vs Python 的字面量）。
