# 数据交接 · 给规则线

**一句话：仓库根 `data/口径表_v4_定稿.xlsx` 已经进来了，但 `data/koujing.json`
还是上一版（v3 草稿）生成的，两个方向都落后。**

`koujing.json` 是 规则层 `app/rules/koujing.py` 和前端 `src/data/koujing.ts`
**共用的那一份**，也就是 G1 闸门和输入框确认条都在读它。所以下面每一条都会
同时影响后端闸门和前端提示条。

> 发现时间 2026-09-29，发现人：接口线。改动没做，交给你 —— `koujing.py` 和
> 这份 json 是你的文件，我越线改会和你的改动撞车。

## 一、先确认这不是我搞错了版本

`koujing.json` 的 `元数据` 自己写着：

```
来源: 口径表_v3草稿_待改错(3).xlsx · 工作表「口径表(草稿)」
状态: 草稿
警示: 原表标题写着「待改错」：限额数字与部分时效业务方还没确认。
      演示前跟泽晟核对，别把草稿当成定稿讲。
```

仓库根新出现的是 `口径表_v4_定稿.xlsx`，它的 `3_定稿说明` 第一行是
`口径表 · v4 定稿（2026-09-29）`，`4_已知开放项` 写着「3 件（不阻塞开发，
**均已用默认值定稿**）」。

**所以该以 v4 为准，json 需要重新生成。**

## 二、禁语（`绝对不能说`）

json 的 `禁语` 字段对应 v4 的 `绝对不能说` 列。按编号合并同编号行后逐条比：

| 编号 | v4 定稿 | json（v3） | 后果 |
|---|---|---|---|
| **K04** | 有 `任何情况都包邮` | **无** | **少拦一句** |
| **K06** | 有 `任何诊断性表述` | **无** | **少拦一句** |
| K09 | `假一赔十（除非公司确有该承诺）` | `假一赔十` | 判据措辞变了 |
| K09-01 | 承接 `绝对最低价`／`比任何渠道都便宜` | 挂在 K09 名下 | 编号对不上 |
| K03 | 列里仍是 `保证X天到账`（带占位符 X） | 已移入 `禁语模式` 正则 | **json 是对的，别改回去** |
| K03-01 / K03-02 | 新增行，禁语**为空** | 没有这两行 | v4 自己记为开放项 |

K03 那条单独说明一下：v4 原文里 `保证X天到账` 带着占位符 `X`，**字面匹配永远
打不中**。json 的 `备注` 里记着当时把它改写成 `禁语模式` 正则
（`保证.{0,4}天.{0,2}到账`）。**这是 json 比源表更对的一处，重新生成时别丢。**

## 三、`可以说`（表述边界）和 `推荐标准话术`

这两列也是**运行时三项**（v4 字段说明原话：「公司允许说到哪一步」是话术必须
落进去的范围，「推荐标准话术」是生成时的定表述）。v4 改了几处：

### `可以说`

| 编号 | v4 定稿 | json（v3） |
|---|---|---|
| **K04** | 按退货原因自动判断：「七天无理由」或「过敏／使用不适」→ 运费由我们承担；其他原因 → 按平台规则处理，**不主动承诺包邮** | 质量问题导致的退换货，运费由我们承担；非质量问题的运费按平台规则处理 |
| **K05** | 补发**在**48小时内发出 | 补发**一般在**48小时内发出 |
| K09 | ……都是进口。只要是在官方授权的【正规渠道】购买都可以**放心**使用 | ……都是进口，**【商品支持正品验证】**。只要是在官方授权的【正规渠道】购买都可以**正常**使用 |

K04 两条都是实质变化：范围**扩**到「七天无理由」（v3 只写质量问题），同时
**新增限制**「不主动承诺包邮」。

K05 去掉了「一般」这个软化词 —— 而同一行的 `依据来源` 标注仍是**待确认**。
**措辞收紧了但来源还没确认**，这两件事放一起看不太对，值得跟业务方再确认一次
是笔误还是有意。

### `推荐标准话术`

只有 **K04** 变了：`如果是质量问题或过敏导致的退货，运费由我们承担；其他情况
按平台规则处理……`

## 四、json 少四个字段，其中两个是结构缺口

v4 的列 vs json 的条目字段：

| v4 列 | json | 说明 |
|---|---|---|
| `依据来源` | **没有** | ⚠️ v4 字段说明写明它是 **G3 来源可回查** 的依据 |
| `来源标注` | **没有** | 标注=公开政策／官方字段／品类通识／待确认 |
| `顾客常见问法` | **没有** | v4 说「25 未规定用途；可作意图识别的种子词」 |
| `客服现在可能说的(风险说法)` | **没有** | ⚠️ 见第六节，**这是现成的测试数据** |
| （v4 没有） | `禁语模式` | json 自己的改进，保留 |

**`依据来源` + `来源标注` 这两列是真缺口，不只是「值要更新」。** G3 要求
「引用的依据必须真实存在」，而现在 json 里没有任何依据可查 —— 这一步没有数据源。
`口径表_v4_定稿.xlsx` 的 `2_依据来源` 工作表还有 5 条权威依据（药监局分类规则、
卫健委孕期提示、化妆品监督管理条例第22条等），是可直接用于答辩的。

## 五、几处要你判断的

### 1 · `严重度` 还参不参与判定？

v4 字段说明：

> `严重度` | ⚠️ **不参与判定** | §九 重定义后，判断依据是"有没有真冲突"，不是话题类别／严重度。**保留仅作参考**

而 `koujing.py:174` 现在写着：

> 按严重度从高到低扫，不是按编号 —— 原实现按 K01→K20 顺序返回，那样
> K19「绝对适合你」会盖过 K01「孕妇可以用」。同一句话命中两条时，

**这里是冲突还是两回事，只有你能判断。** 「不参与判定」可能只是说「命中与否
不看严重度」，也可能包括「排序也不该看」。如果是后者，`匹配` 的排序键要换一个
（换什么？命中位置？编号？）—— 换排序会动 `test_rules.py`。

### 2 · `guards.py:284` 那段「待核对」工作还作数吗

`guards.py` 里有一处注释说「口径表自己标着『待改错』，K03/K05/K07 的时效数字
……」。v4 的 `3_定稿说明` 第五节正是业务方对这几条的答复原话（含 K03
「不改天数，用 1-3 个工作日，以银行入账为准」）。

**定稿之后那段兜底逻辑可能已经没有存在理由了** —— 或者它还该留着，因为 K05/K07
的 `来源标注` 在 v4 里仍然是「待确认」。

### 3 · json 的 `元数据.待核对` 和 v4 的 `来源标注` 打架

json 现在列了 K03／K05／K07 三件待核对。v4 里 K03 的 `来源标注` 是 **已确认**，
K04／K05／K07 是 **待确认**。

也就是说 v4 把「这条到底确没确认」做成了**逐行的列**，比 json 那份手写的三行清单
更细。看起来该换成 `来源标注`。

> ⚠️ **但换之前先看这条链 —— 它会静默失守。**
>
> ```
> 元数据.待核对  →  koujing.待核对数字()  （读的就是这里的「值」）
>                →  guards.G3来源可查(待核对=…) 的第 3 条降级
> ```
>
> 现在的值是 `{'48 小时', '价保时效（原表未给具体时限）', '1-3 个工作日'}`。
>
> 把 `待核对` 删掉或改名，`待核对数字()` 就返回空集，**G3 的第 3 条不再命中** ——
> 那些业务方从没点过头的数字会被闸门放行。而**没有任何测试会红**：
> `tests/` 里 `待核对` 一个引用都没有（我 grep 过了），`guards.py` 那段注释
> 说的「第 3 条把它降成中危」会变成一句空话。
>
> 真要换成 `来源标注`，`待核对数字()` 得一起改，**并且顺手补一条测试**。
> 这属于「删字段顺手删掉了行为，而行为没有测试」那一类，最不该留给你之后才发现。

## 六、v4 自己交代的事，两条

### 1 · 「去痘」还没进表

`4_已知开放项` 第 1 条，原话：

> `25` §13.1 已确认要新增的禁语「去痘／去除痘痘」，本表还没有。……
> 当前采用值：**暂未加入（队长指示"先不动"）**。检查一暂时拦不到「去痘」这类说法

**这是已知缺口，不是 bug。** 如果有人问「为什么『去痘』没被拦」，答案是这条。

### 2 · `风险说法` 列 = 现成的 G1 负样本

v4 字段说明对这一列的用途写着：

> `客服现在可能说的(风险说法)` | 测试用 | **G1 的负样本** —— 拿这些句子跑一遍，
> 检查一应该全部命中

**业务方给的负样本集。** 拿它建一条参数化测试，比我们手写样本强得多：每一行
都是「打这句话 → 应该命中该行的话题编号」。正好能喂进「剧本当验收层」那套。

## 七、改的时候别碰的三件事

1. **`禁语模式` 不要删。** v4 里没有这一列，它是 json 补的；K03 靠它才对得上。
2. **`补充禁语` 和 `替换说法` 两块不在 `1_口径表` 里**，v4 没覆盖到它们，
   重新生成时原样保留。

   附带一个观察：`koujing.py:86` 那段文档串说「K09 的『可以说』里写着
   【保证100%正品】，同一个词又在补充禁语里按高危拦」，并据此称这条校验
   必须常驻。**v4 定稿把 K09 的「可以说」改了**，那句正品表述已经不在里面 ——
   所以那段注释描述的是历史，不是当前会触发的约束。校验本身该留（换一份表
   就可能漂回来），但**注释里的例子需要更新**，否则下一个人会照着找一个
   已经不存在的东西。
3. **`元数据.来源` / `状态` / `警示` 三行要一起改**，不然下一个人打开 json
   还是会看到「草稿」和「待改错」。

## 八、改完跑这些

```bash
cd backend && PYTHONIOENCODING=utf-8 .venv/Scripts/python.exe -m pytest -q
cd frontend && npx tsc -b --force && npx oxlint
```

前端那条是 `tsc -b`，**不是 `--noEmit`** —— 根 `tsconfig.json` 是 solution 式的
（`files: []` ＋ `references`），`--noEmit` 打它等于什么都没查而且 exit 0。

`koujing.ts` 只是把 json 包成带类型的接口（它 import 的是 `@data/koujing.json`），
所以**值的变化前端不用改代码**；只有新增字段（`依据来源` / `来源标注`）才要动
那个 interface。
