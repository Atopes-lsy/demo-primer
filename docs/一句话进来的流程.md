## 术语 · 三个词的约定（2026-10-01 定）

**这是本份文档的地基，下面所有节点都按这三个词读。**

| 词 | 定义 | 粒度 | 谁定 |
|---|---|---|---|
| **诉求** | 顾客要办的那一件事 | **可跨轮、跨天** | 装配层 |
| **轮** | 围绕**同一诉求**、买卖双方往来的**多条**消息 | 跨消息、跨双方 | `认诉求` ＋ 切轮 |
| **主张** | **一条消息里**一个能独立处置的事实点 | 消息内，N 条 | 拆主张（LLM） |

包含关系：**诉求 ⊃ 轮 ⊃ 主张**。一条消息拆出的 N 条主张**全部归入当前轮**。

### 为什么是这三个词

v8 用「**事实点**」同时界定两样东西：

| 出处 | 界定谁 | 判据 |
|---|---|---|
| §1.2 | 「轮」 | **没写** |
| §二 | 「主张」 | 「能不能单独产出一个输出」 |

于是**拿主张的尺子去量轮**。在 v8 自己举的例子「这精华里有乙醇吗？我是孕妇能用吗」
上会量出两个答案：按轮该是两条，按主张也是两条 —— 但两把尺子的**对象**根本不是一回事。

定这三层之后，那个例子是：**一条轮、两条主张**
（含乙醇 → AI直发；孕妇能用 → 客服点发送 ＋ 边界句）。

### 据此要修的一处 v8 措辞

- v8 §1.2 原文「『一轮』用**事实点**界定」→ 应为「用**诉求**界定」
- v8 §二「一条主张 ＝ 一个能被独立处置的事实点」→ **不变**

> **为什么值得单独立一节。** 这两个词混用不会让任何东西报错 —— 代码里两边都能跑，
> 测试也不会红。它只会在**验收的时候**咬人：拿主张的条数去数轮，或者反过来，
> 两边数的根本不是一回事，却都觉得自己对。⑭ 和 ④ 两条矛盾是同一次混淆的两面。

# 第一部分 · 逐节点技术清单

## 节点 0 · 上下文装配

| 项 | 内容 |
|----|------|
| **做什么** | 从「会话ID」把这一轮判定要用的全部上下文拉齐，装配成「顾客情况」五行 |
| **输入** | 会话ID + 新到的一条消息 |
| **输出** | 顾客情况（固定五行）、当前订单、当前工单、历史消息 |
| **数据结构** | `StateRow { 标签, 值, 备注?, 警示? }`，顺序固定：这是谁 / 这次要什么 / 答应过什么 / 办过什么 / 这单 |

**技术选型**

- **关系连接**：全部按 `会话ID` 直连，不用图查询也不用 join 链。约束是「一个会话
  至多一笔订单、至多一张工单」，所以订单和工单都是**单值而非数组** —— 这是整个
  数据模型的地基，省掉了「一个会话多张工单该怎么合并」这类问题。
- **多表枚举**：五张工单表（补发换货 / 线下打款 / 物流 / 不良反应 / 售后退货）结构
  不同，要用**判别联合**（可辨识联合 / tagged union）承载 —— 前端 `TaggedTicket`
  就是 `{ kind: TicketKind; ticket: AnyTicket }`，`kind` 决定渲染哪套字段。
- **会话状态对象**：判定是「一条消息进来 → 产出右栏状态」，但顾客情况、承诺时限、
  已发出的话术都要跨消息存活。所以需要一层**会话级状态**，它不是任何单张表。
  前端是用 React state 里的 `Session` 承担这个角色。

**技术上的死结**

- 五行的值全部是**自然语言**（`值: '9/26 承诺「今天答复」'`），但下游要用的是
  **结构化值**（H3 要 `datetime`，G4 要能字符串匹配的「办过什么」）。
  中间缺一层「自然语言 → 结构化」的解析，而这一层无论用规则还是用模型都有代价（见矛盾 ③）。
- 「每条消息都重读」保不保证幂等？五行里「这是谁」「这单」在一轮对话里根本不变，
  全量重算既是浪费，也让留痕无法重放（见矛盾 ⑫）。

## 节点 1 · 输入安全层

| 项 | 内容 |
|----|------|
| **做什么** | 在消息到达模型之前，判定它能不能进判定流程 |
| **输入** | 买家消息原文 |
| **输出** | `安全事件[]`，每条带 `类别 / 命中 / 处置 / 说明` |
| **关键约束** | 拦截类的命中片段必须是**脱敏后**的 |

**技术选型**

- **正则匹配**（`re.compile` 预编译），四组词表：注入 / 违规 / PII / 辱骂。选正则不选
  模型，理由是**延迟和攻击面**：这是链路最前面，必须微秒级；而且要拦的东西
  （提示词注入）恰恰是模型最不可靠的地方。
- **两分处置表**，不是严重度分级：

  | 类别 | 处置 | 设计理由（代码里写明的） |
  |------|------|------------------------|
  | 注入 / 违规 | 拦截 | 「这类消息一旦进了模型，产出的判定结果就没法信了」 |
  | PII / 辱骂 | 标记 | 买家发证件号正是要办业务；客服被骂是常态，该做的是升级情绪不是拒收 |

- **脱敏算法**：保留前 3 后 4，打码后**长度不变**。长度不变是有用的性质 ——
  客服还能核对是不是同一个号、位数对不对，但还原不出原号。
- **去重**：`已记` 集合，防止一个手机号被「银行卡号」规则重复命中。

**技术上的死结**

- **正则拦不住注入。** 谐音、变体、图片、语音、多语言都是绕过路径。设计里没有任何
  兜底 —— 没拦住的注入会直达 LLM。这是「够用就好」的取舍，但要有意识地承认它。
- 违规词表**明写是占位**，真上线要换成内容安全 API。换 API 会引入**网络调用**，
  这一步的「微秒级」前提就没了，而它上面压着「能短路」的整个论证。

## 节点 2 · 硬触发 H1–H4

| 项 | 内容 |
|----|------|
| **做什么** | 从原始消息和顾客情况里报告风险事实，不判定 |
| **输入** | 消息列表 + 当前时间 + 承诺时限 + 订单状态 |
| **输出** | `触发[]`：编号 / 名称 / 严重度 / 证据 / 说明 |

**技术选型**

| 触发 | 算法 | 参数 |
|------|------|------|
| H1 风险 | 三组词表包含扫描（人身 / 监管 / 舆情） | 人身或监管 → 高；只有舆情 → 中 |
| H2 情绪 | 词表扫描 ＋ **模型**（仅第 ⑤ 条） | v9 §三 六条判据：①时间施压 ②维权威胁 ③要求方案 ④负面情绪 ⑤不信任 ⑥重复要求 |

**处置上只有 ③要求方案 ＋ ⑤不信任 走转交短路**（2026-10-01 定，决策「丙」）。
①④⑥ 命中时照常记进 `触发[]` 和留痕，**但不短路** ——「什么情况」「咋回事」
是极高频率的日常口语，当转交信号会让演示现场随便一句吐槽就翻车。
②维权威胁的 7 个词**全部落在 H1 的词表里**（`12315`／`消协`／`法院`／`举报` 属监管，
`投诉`／`曝光`／`差评` 属舆情），所以它本来就跟着 H1 走，**不额外增加转交**。

> **这条把「判据表」和「处置表」解耦了。** v9 §三 那张表回答的是「什么情况算情绪升级」，
> 是个**判据**问题；这里回答的是「升级了要不要整通转出去」，是个**处置**问题。
> 混在一起读，就会得出「六条判据 = 六种转交」，而那既没必要（①②本来就重复）
> 也不安全（④会把日常吐槽全踢出去）。
| H3 逾期 | `datetime` 比较 | 逾期 ≥1 天 → 高 |
| H4 风控 | 词表扫描 + 订单状态提升 | 高危状态：已签收 / 交易成功 / 已完成 |

- **无状态纯函数**：四个触发函数都不读全局、不取 `datetime.now()`，`当前` 由外部传入。
  这是为了**可重放** —— 同一份输入跑两遍必须得出一模一样的结论，否则演示时没法解释。
- ~~**H2 的归一化**：先 `re.sub(r"[\s\W_]+", "", t)` 再去数。~~ **已作废** ——
  这段归一化是为「连发检测」服务的，而 v9 把连发**点名判成死代码**
  （「实测 138 个会话里根本触发不了」）。`triggers.py` 里已经没有这行正则了。
  六判据里唯一靠模型的第 ⑤ 条要求**引用原句**，正好和「抹掉格式再比」相反。
- **稳定排序**：`sorted(key=lambda t: (0 if 高 else 1, t.编号))`。同级按编号定序，
  保证留痕两次跑出来顺序一致。

**技术上的死结**

- **H3 的输入是自然语言。** `承诺时限` 要从「9/26 承诺『今天答复』」里解析出来，
  而且「今天」是相对**承诺发生的那一刻**（9/26）而言的，不是相对当前 ——
  解析它必须先知道承诺是什么时候说的（自指问题）。
  用规则解析脆，用模型解析就**把模型塞进了自称「纯规则、能短路」的那一层前面**（见矛盾 ③）。
- **H2 的窗口是「本轮」，但触发单位是「一句话」。** 逾期检测需要跨轮状态、
  G4 需要历史上所有发出的话。判定单元和状态单元对不上（见矛盾 ④）。
  （原先这里还举「连发检测需要最近几条买家消息」，那条已作废 —— 见上。）
  **→ 已定（2026-10-01）：轮按诉求切，归属由节点 3.5 的 `认诉求` 判。**

## 节点 3 · 拆主张

| 项 | 内容 |
|----|------|
| **做什么** | 把一句话拆成若干条独立的「主张」 |
| **输入** | 买家消息 + 顾客情况 |
| **输出** | 主张列表（`Disposition.主张` 是它的最终落点） |

**技术选型**

- **LLM + 结构化输出**（JSON Schema / function calling 约束成数组）。
  一句话里可能同时有「问成分」「要补发」「投诉」三件事，规则拆不开。
- **主张是下游唯一的归因单元。** 每一条主张最终要变成一条
  `Disposition { 主张, 输出, 说明 }`，一条主张配一种 `OutputKind`。

**技术上的死结**

- ~~粒度没有定义~~ **→ 已定义（2026-10-01）**：一条主张 ＝ 一个**事实点** ＝
  一个能独立处置的点。「含乙醇」和「孕妇能用」是**两条**（两种输出）。
  它们是否属于同一**诉求**，那是节点 3.5 的事，**不影响主张的条数**。

  > 原文（保留，因为它记的是当时的困惑）：「孕妇能否用」是一条主张，「含乙醇」也是一条。
  > 但「孕妇能否用」同时涉及成分和个体差异 —— 拆成一条还是两条？
  > 粒度直接决定下游产出的处置条数，粒度不定，判定结果就不稳定。
  >
  > **那个「同时涉及」的困惑是把两把尺子叠在一起量出来的** —— 见术语节。
- **主张没有 ID。** 「本轮处置」的渲染用主张文本当 React key（`key={d.主张}`），
  意味着**主张文本就是主键**。同一轮里两条主张文本相同（或跨轮重复）就会冲突。

## 节点 3.5 · 认诉求（新增，2026-10-01）

| 项 | 内容 |
|----|------|
| **做什么** | 判这条消息**属于**已有的哪个诉求；不属于任何已有的 → 起一个新诉求 |
| **输入** | 一条消息 ＋ 本会话当前未解决的诉求清单 |
| **输出** | 诉求归属（已有的某个 ／ 新建） |

**技术选型**：模型。这是链路里的**第七个模型位置**。

**为什么不能并进拆主张。** 催促可能**拆不出任何主张** ——「还要多久」不是一个
「能独立处置的事实点」，按 v8 §二 该拆出零条。但它的**归属是必须的**：
H2 的窗口要它、G4 防重复要它、小卡要它。

> **归属问题在主张列表为空时依然存在，所以不能靠拆主张的输出来带。**

**顺序影响**：本节点排在拆主张**之后** —— 归属判不了就分不出轮。`切轮` 因此
一分为二：判归属的那半交给本节点，**按归属标签分组**的那半留在 `切轮` 里，仍是纯规则。

> ⚠️ **这条把一个已经承诺出去的性质收回了**：`pipeline.切轮` 原先**标着纯函数**
> （「这条函数是纯的（同一输入必得同一输出，可重放）」，`pipeline.py:777` ——
> **引行号会漂**，这句话在同一天里从 `:759` 漂到了 `:777`、10-02 已漂到 `:864`，
> 定位请用引文本身），而整段「规则层可重放」的论证建立在它之上。`认诉求` 进来之后，
> 收窄的是「**不需要额外输入**」（归属表从模型来）；**「同样输入同样输出」没收窄**
> —— 归属一旦给定，`切轮` 对它仍是纯的，留痕拿到 `归属` 就能重放怎么切的。
> 可重放的范围缩到「**归属表之后的**规则层」。这不是加个模型位，
> 是改一句已经写出去的承诺。

## 节点 4 · 三层判定

| 项 | 内容 |
|----|------|
| **做什么** | 把「事实」（触发命中）和「主张」判成具体的输出类型 |
| **输入** | 主张列表 + 硬触发事实 + 顾客情况 |
| **输出** | 每条主张 → 一种 `OutputKind` |

**技术选型**

- **枚举优先级 + 取最大值**：

  ```
  AI直发(0) < 客服点发送(1) < 报备(2) < 转交(3)
  ```

  一轮里多条主张 → 取最高态渲染主卡，其余全部进「本轮处置」逐条可查。
- 取最高态是为了解决一个具体的问题：**一轮里可能有三种输出，但主卡只有一张。**
  不做取舍的话，客服会以为 AI 抢了他的活，或者漏做了什么。

**技术上的死结**

- **「三层」的三层没有定义。** 名字出现在注释里，但没有地方说明每层判什么、
  规则表长什么样。
- **优先级是单一数值轴，但要排的是两类不同性质的东西。** 「报备」是权限问题
  （事该办，但越过我的额度）；「转交」是路由问题（这事我不该碰，交给专人）。
  把它们压到一条数轴上取最大值，只能决定**显示哪个**，决定不了**其余动作还执不执行**（见矛盾 ⑦）。
- **`Advice.形态` 只有三种**（需要话术 / 需要授权 / 有风险），没有「无需动作」这一种。
  一轮里只有 AI 直发时，主卡该显示什么？（见矛盾 ⑥）

## 节点 5 · 依据检索

| 项 | 内容 |
|----|------|
| **做什么** | 为这轮判定和话术生成准备「依据清单」 |
| **输入** | 主张 + 顾客情况 |
| **输出** | `Evidence[] { 序号, 出处, 摘要, 用上 }` |

**技术选型**

依据来源性质不同，检索手段也不同 —— 这是这一步最关键的技术分叉：

| 性质 | 来源 | 检索方式 |
|------|------|---------|
| **结构化** | 订单、五张工单、商品 | 按 `会话ID` / 订单号精确查 |
| **半结构化** | 口径表 K01–K20 | 按主张的话题关键词匹配 |
| **非结构化** | 商品属性表、先例库 | **向量检索**（`pgvector` 已在依赖里） |

> **2026-10-06 追记 —— 这一行两半都要改，其中一半是「早就错」。**
>
> **① 那半（一直不成立）**：商品属性表**从来不是向量检索** —— 它是按货号
> **精确连接**（`检索/商品表.查商品` 就是 `表.get(货号)`；20 行、无 top-K、
> 无相似度阈值），落地时就是这个口径。把它归成「非结构化」也站不住：
> 它是一张有主键（货号）的表。
>
> **③ 那半（现在成立了）**：先例库**真走向量召回**了 —— 2026-10-05 建的库
> （139 条），`text-embedding-v4`，阈值 0.63，取 3 条。**但它不进六源**，
> 走 prompt 第 6 块（风格来源）。
>
> **另外**「`pgvector` 已在依赖里」也不成立了：它已从依赖里摘掉
> （`backend/pyproject.toml:15` 写着「故意没有」）。

- **必须带出处。** 每条依据要有「表名 + 行号」形状的出处（如「口径表 K05」），
  这是 G3「来源可查」闸门的输入，也是客服点开「这句话为什么站得住」时看到的内容。
- **用上的和没用上的都要列。** 设计意图是「列全是为了证明没有遗漏」。
- **展示形态：默认折叠（规格 v9 修订）。** 折叠态一行，**必须带命中数**：
  `▸ 依据 · 3/6 源命中`。展开态三部分，顺序固定：
  命中来源逐条列出 → `另 3 源无记录 · 一并列出以示无遗漏` → 未命中的六源清单。

  > **为什么折叠不伤「底气」。** v8 原本写「常显不折叠」，理由是「底气必须一眼可见」。
  > v9 依实现方意见改回折叠，但保留了一条底线：**折叠态不能只剩「依据」两个字**。
  > 差别在于客服能不能看出「系统查过没有、查到几条」——
  > 带上 `3/6`，折叠是入口；只剩「依据」两个字，折叠是把入口也一起藏了。
  >
  > **这个「3/6」的分母之所以成立**，正是因为依据的粒度是**六个来源的封闭集合**，
  > 而不是 top-K 召回结果（见矛盾 ⑨ 的更正）。换个检索口径，这个分数就报不出来。

**技术上的死结**

- **「证明没有遗漏」和 top-K 召回是矛盾的。** 向量检索天然截断，你能证明的只有
  「top-K 里没有遗漏」，证明不了全集。要真证明没遗漏，得对每个主张遍历全部来源 ——
  那是全表扫描不是检索（见矛盾 ⑨）。
- **依据清单同时服务两个读者，而两者的信息需求不同。** 生成侧要的是「相关的都给我」，
  展示侧要的是「用上的 + 为什么没用上」。先例库在演示数据里 `用上` **永远是 false** ——
  它只对生成侧有意义，但它出现在展示侧的清单里。

## 节点 6 · 话术生成

| 项 | 内容 |
|----|------|
| **做什么** | 按口径和依据写出一句能发的话 |
| **输入** | 主张 + 依据 + 口径表 + 顾客情况 |
| **输出** | 话术文本 |

**技术选型**

- **LLM + 约束生成**。约束有三层：

  | 约束 | 来源 | 强度 |
  |------|------|------|
  | **上界** | 口径表的「可以说」 | 弱 —— 自然语言，模型是「尽量遵守」不是「无法违反」 |
  | **示例** | 口径表的「标准话术」 | 中 —— 当 few-shot 用，或当兜底直接发 |
  | **依据** | 节点 5 的依据清单 | 中 —— 不允许超出依据，由 G3 事后验证 |

- **约束强度是弱的是有意的**：设计上不指望模型一次说对，靠节点 7 的闸门兜底。
  「**这套闸门是话术模型不必完美的原因**」—— 这句话是整个技术选型的支点，
  它让模型可以选便宜的那一档。

**技术上的死结**

- **「可以说」当上界，前提是「可以说」和「禁语」互斥。** K09 曾经打破它 ——
  「可以说」列里就写着被列为禁语的 `保证100%正品`。**这条已经按「清干净」处理了**
  （见矛盾 ⑤ 与下面的四追记）；但「两个集合在设计上是否保证互斥」这个问题，
  口径表本身并没有回答。
- **用自然语言当约束，约束的是「意思」，但闸门验的是「字面」。** 模型完全可能
  换一种说法表达同样的越权承诺，字面闸门拦不到。

## 节点 7 · 出站闸门 G1–G4

| 项 | 内容 |
|----|------|
| **做什么** | 话术发给顾客之前过一遍 |
| **输入** | 话术 + 依据 + 已发出的话 + 顾客情况 |
| **输出** | `闸门命中[]`，空列表表示放行 |

**技术选型（四道门的机制完全不同）**

| 闸门 | 技术 | 具体算法 |
|------|------|---------|
| **G1 禁语** | 子串扫描 + 正则 | 遍历口径表逐条 `word in text`；带占位符的用 `禁语模式` 正则 |
| **G2 边界** | 子串扫描 + 正则 | 硬组 8 词判高（阻断）、软组 7 词判中（只记录）；越权承诺用正则（动词 + 金额/时限） |
| **G3 来源可查** | 正则抽 + 归一化比对 | `\d+单位` 抽数字 → 去掉空白后查是否出现在依据或可引用文本里 |
| **G4 防矛盾** | **2-gram 集合 + 重合度** + 正则 | 重合度 = \|交集\| / min(\|A\|,\|B\|)，阈值 0.75；「已 + 动作词」断言查「办过什么」 |

- **G4 为什么用 2-gram 而不是分词**：中文没有空格，字级切分比词级稳（不依赖词典）。
- **G3 的归一化**：「48 小时」和「48小时」是同一个数，比对前先把 `\s+` 去掉。
- **放行规则**：**只有「高」严重度才阻断**。中危只记录 —— 客服自己能判断。
- **稳定排序**：同严重度按闸门编号排，保证留痕顺序一致。

**技术上的死结**

- **G2 自称「拦的是句式不是词」，但实现是子串匹配一个词表。** 和 G1 机制完全同构，
  只是词表来源不同（G1 的词有口径编号，G2 的词是硬编码）。真正拦句式的只有
  `G2越权` 那一条正则（见矛盾 ⑧）。
  **代码后来自己承认了这一点** —— 现在那两组词表挂在 `G2措辞` 名下，文件头明写
  「不是规格里的 G2」；`G2边界句` 是另一件事（查该带的那句话在不在）。
- **「带反馈重生成」对所有命中不都适用。** G3 命中「数字编造」重生成有意义；
  G4 命中「谎称已经补发」**重生成修不了** —— 那是事实错误，需要回去查工单
  （见矛盾 ⑩）。
- **依据为空时死循环。** 节点 5 召回空 → G3 判「没有任何依据」→ 重生成 →
  还是空 → 再拦。兜底机制本身没有出口（见矛盾 ⑩）。

## 节点 8 · 输出派发

| 项 | 内容 |
|----|------|
| **做什么** | 把判定结果派成具体动作 |
| **输出** | 四种输出 |

**技术选型**

- **枚举 + 优先级取值** 决定主卡形态。
- **前端的状态载体**：`草稿` / `报备{等待分钟, 工单号}` / `转交{工单号}` 全部挂在
  会话对象上，切走再切回来不丢。

**技术上的死结**

- **「已执行的动作」和「待执行的动作」混在同一根优先级轴上。** ① AI 直发是
  **已经发出去**的既成事实（聊天区里已经有那条消息），②③④ 是**等客服点按钮**。
  取最高态只能告诉你「该显示哪个」，告诉不了你「已经做了什么」（见矛盾 ⑦）。

## 节点 9 · 客服侧校验

| 项 | 内容 |
|----|------|
| **做什么** | 客服打草稿 → 每次编辑都校验 → 命中就提示 |
| **输出** | 确认条：［一键替换］［仍然发送］ |

**技术选型**

- **每次渲染重算，不存进 state。** 设计理由：客服改一个字，提示就该跟着变。
  存 state 会出「改了字还挂着旧提示」的 bug。
- **一键替换用字符串 `replace`**。
- **措辞是「确认」不是「拦截」**：保留［仍然发送］，最终决定权在客服手里。

**技术上的死结**

- **一键替换没有收敛性保证。** `replace` 是全量替换（禁语出现多次全换），
  替换后的建议文本可能命中另一条禁语，下一次渲染又报警 —— 打地鼠。
- **客服手写的草稿只过 G1 一道闸门。** AI 生成的话要过 G1–G4 四道，
  人写的话只过查表这一道。可以写「保证明天到」（G2 该拦的越权承诺）、
  可以编数字（G3 该拦的）、可以和上一句重复（G4 该拦的）（见矛盾 ⑪）。

## 节点 10 · 留痕

| 项 | 内容 |
|----|------|
| **做什么** | 记下每一轮判了什么、依据是什么、谁越过了哪条口径 |
| **输出** | 追加写、不可改的日志 |

**技术选型**

- **append-only 日志** + **写前脱敏**。脱敏放在写入前而不是展示前，因为
  「留痕表要长期保存，原样记下手机号等于把审计日志变成泄露源」。
- **可重放要求**：同一份输入跑两遍得出一模一样的结论。这在规则层是靠
  「时间外部注入 + 稳定排序」实现的。

**技术上的死结**

- **可重放和 LLM 不能共存。** 拆主张、话术生成都是模型调用，同样的输入
  未必出同样的输出。**「判定必须可重放」这条要求，在链路上存在 LLM 的那一刻就断了**
  （见矛盾 ⑫）。

> **2026-10-06 落地记录（步骤 6，`api/留痕.py`）—— 上面两处与本文件其余部分的口径对账：**
>
> - ~~「append-only 日志」~~ → **一半对**。**动作**（`报备`／`转交`／`发送`／`完成`）
>   是真追加，**只增不改**；**轮次**是**同一轮后写盖先写**（和 `台账` 原来那条规矩
>   同义）—— 回放端拿轮次当主键，留两条「第 2 轮」取哪一条都不对。**「不可改」
>   这一句对轮次不成立**，别照这句讲。
> - **「写前脱敏」照做了**，但**比这里写的多一层**：`inbound.脱敏` 盖的是 `扫输入`
>   抓出来的那一小段，整段原文还在，所以留痕自己过一遍 `全篇脱敏` ＋ 一个递归的
>   `_洗过`（见 `_六源条` 上面那段 —— **模型抄回来的主张也是买家原话**，
>   计划里四处过滤一开始漏了它）。
> - **「可重放」的范围收窄成「切轮之后的规则层」** —— 留痕存了 `轮消息` ＋ `归属`，
>   拿这两样重跑 `pipeline.切轮` 能逐条复原当时切出来的轮次边界（2026-10-06 真打验过
>   两条演示线）。**六个模型位不承诺可重放**，只承诺「有一次完整调用记录」
>   （原始 prompt／回答／token 都在 `模型调用[]` 里）。矛盾 ⑫ 因此**答了一半**：
>   规则层答了，模型层答不了。

# 第二部分 · 流程自身的矛盾

按「会不会当场翻车」分三档。

## A 档 · 直接讲不通

### ① 拆主张到底跑不跑？两处说法正面冲突

> `inbound.py`：**规则决定要不要转交，拆主张只负责把风险归到哪条主张上供「本轮处置」展示**
>
> `triggers.py`：H1 一旦命中，输出必然是转交 —— **这时候拆不拆主张对结论毫无影响**

**不能同时成立。** 前者说 H1 命中后拆主张照跑（因为要把风险**归到哪条主张上**），
后者说 H1 命中后拆主张可以跳过（因为对结论无影响）。

这不是措辞问题，是**短路点画在哪**的问题：

- 如果短路在拆主张之前 → 省一次模型调用，但「本轮处置」里**不会有新主张**，
  只能保留历史。那 H1 命中那一轮的处置清单就是空的。
- 如果拆主张照跑 → 省不下模型调用，「少一次调用就少一个攻击面」的论证不成立。

**演示时会翻车的地方**：剧本第六步（H1 命中，「刺痛」「投诉」）的终态里，
`本轮处置` 是**六条主张** —— 前四条是历史遗留、后两条是这一轮新拆出来的
（`用后泛红刺痛` / `要求投诉`）。这等于选了第二条路，但那样 `triggers.py`
文件头那段「能短路」的论证就得删掉。

### ② 拦截的定义是「不进流程」，但拦截的出口是流程的产物

> `inbound.py`：拦截 —— **不送进判定流程，直接转交人工**

**转交是四种输出的第 ④ 种**，是判定流程跑完才产出的东西：它要主卡形态
「有风险」、要风险标签、要交接单号、要顾客情况。

于是：**拦截说不进流程，可转交又是一条流程输出。** 那么被拦截的消息：

- 要不要装配顾客情况？（右栏要渲染，看起来要）
- 要不要跑硬触发 H1–H4？（跑了才能给主卡文案）
- 要不要拆主张？（拆了就有主张，和「不进流程」矛盾）
- 主卡显示什么形态？

如果这些都不做，右栏拿什么渲染？如果都做，那「不送进判定流程」这句话
指的就只是「不拆主张」—— 那它和矛盾 ① 是同一个问题的另一面。

### ③ H3 的输入决定了它不可能是「纯规则、微秒级」的那一层

> `triggers.py`：**为什么硬触发要排在拆主张前面** —— 拆主张是 LLM 调用，秒级；
> 这里是正则，微秒级

但 H3 的入参 `承诺时限` 是 `datetime`，来源是顾客情况那一行：
`值: '9/26 承诺「今天答复」'`。**要从这句话里拿到 9/26 24:00 这个时刻，
规则解析极其脆**（「今天」是相对 9/26 而言的，不是相对当前 —— 得先知道承诺发生在
什么时候才能解析「今天」）。交给 LLM 解析则把模型塞进了 H3 **之前**。

**这时候「微秒级」不成立，而它上面压着整个「能短路、少一个攻击面」的论证。**
换句话说：H3 要么放弃纯规则（那排序理由要重写），要么把「承诺时限」在装配阶段
就结构化地存下来（那顾客情况就不能是自然语言）。

### ④ 判定单元是「一句话」，但三条触发规则需要「一个窗口」

流程的入口是**一条消息进来**（`inbound.扫输入(text)`、`triggers.硬触发(消息, ...)`）。
但：

- H2 的连发检测需要**同一句在最近几条里出现 ≥3 次**
- H3 的逾期检测需要**跨轮的承诺状态**
- G4 的防重复需要**历史上发出去的所有话**

**一条消息进来这个粒度，撑不起需要历史的判定。** 实际必须有「这一轮包含哪几条
消息」的定义（防抖窗口？到客服上一次回复为止？），以及「窗口内的消息怎么和
已经在处理的那次判定合并」。设计里没有任何地方定义这个窗口。

### ⑤ 「可以说」当生成上界，前提是它和「禁语」互斥 —— 但 K09 不互斥

> 口径表 K09 的「可以说」列：…店铺出售的产品都是进口，**【保证100%正品】**。
>
> 补充禁语：**保证100%正品** → 按高危拦截。

同一个词，既在「公司允许说到哪一步」的上界里，又在「绝对不能说」的清单里。

**这不是数据录错了**（原表就长这样，处理是「按更严的处理」）。这意味着
**「可以说」和「禁语」这两个集合在设计上就不保证互斥** ——
那用「可以说」当生成侧的上界就不可靠：模型照上界写，写出来的正好是被拦的那句。

> **2026-09-29 更正：数据侧选了「清干净」，并且做了。** `data/koujing.json` 里
> （a）`保证100%正品` 已从「可以说」**挪进**顶层 `补充禁语`，那条还带一个 `理由` 字段
> 写明为什么：规格 §6.4 与渲染图都把它当禁语，两处不一致时按更严的；
> （b）「可以说」里换成了【商品支持正品验证】；（c）`放心使用` 也一并拿掉了。
> `koujing.校验互斥()` 现在返回 `[]`，互斥这条不变量**在 json 上是守住的**。
>
> ⚠️ **但同一个结构缺陷换了个地方还在**：`data/口径表_v4_定稿.xlsx` 的 K09
> 「可以说」**仍然写着**「……都可以放心使用」，而 `放心使用` 是 **K10 的禁语**。
> 也就是说 **json 和 v4 定稿在这一行上给出的答案相反** —— 代码读 json，业务方签的是 xlsx。
> 这条已经记在 `docs/数据交接_给规则线.md`（第 64 行、第 181 行）与
> `规格v8对齐.md`，**别在这里重复处理**。
>
> 所以 ⑤ 该改口的地方是：它不再是「K09 互斥不成立」，而是
> **「互斥靠的是人手工清，没有机制保证 —— 换一张表就复发，事实上已经复发了」**。

`koujing.json` 的字段说明写的是「『可以说』：公司允许说到哪一步。**生成话术时的上界**。」
当时这句话和 K09 打架。两条出路是「要么清干净（那它就不是原表的原样了），
要么承认上界不保证合法」—— **实际选的是第一条**，所以现在 json 上不打架了；
但「不是原表原样」这个代价真的付了：`补充禁语` 这一层就是为此新加的，
**它是我们对原表的修正，不是原表的内容**。

### ⑥ 只有 AI 直发的那一轮，右栏什么都不显示

`Advice.形态` 只有三种：`需要话术` / `需要授权` / `有风险`。**没有「无需客服动作」这一种。**

而 AI 直发**不需要客服动手，所以永远不当主卡**（这是刻意的设计）。
于是：一轮里如果所有主张都判成 AI 直发，`建议` 为空，右栏只剩下顾客情况
（`PrimerPanel` 在 `建议` 为空时显示「本轮无需客服动作」）。

**但 AI 已经替客服把消息发出去了。** 而显示「谁发了什么」的「本轮处置」
在**输入框下方**，也就是中部，不在右栏。

**矛盾点**：设计意图是「AI 代发必须标出处，客服一眼看出哪句不是自己说的」，
但 AI 直发在右栏（评分区）是隐形的 —— 客服不看输入框下方那一条，就不知道
AI 替他回过话。而 AI 直发恰恰是**唯一不受客服控制的输出**，也是最需要被看见的。

## B 档 · 逻辑不闭合

### ⑦ 取最高态只解决「显示哪个」，没解决「其余动作还执不执行」

优先级 `AI直发(0) < 客服点发送(1) < 报备(2) < 转交(3)` 是**单一数值轴**，但它排的是
两类不同性质的东西：

- **AI 直发**是**已执行**的既成事实（消息已经在聊天区里了）
- **客服点发送 / 报备 / 转交**是**待执行**的动作（等客服点按钮）

把「已经做完的」和「等你做的」压到一根轴上取最大值，只能得出主卡显示什么。
**没定义的是：主卡显示 ④ 转交时，同一轮里那两条 ② 报备还提不提交？**

剧本第六步就是这个局面：赠品漏发 → 报备，逾期未答复 → **转交**，
用后泛红刺痛 → 转交，要求投诉 → 转交。主卡显示「立即转交」。

> **2026-09-29 更正：第 6 步的「逾期未答复」不是报备，是转交。**
> 第 5 步那一轮只有 H3，判的是报备（对话还在客服手里）；第 6 步 H1／H2
> 在同一轮命中，**硬触发短路是整轮生效的** —— 对话都转出去了，「走个审批」没有意义。
> 所以那一条被改判成转交，说明写的是「同轮 H1／H2 命中 —— 整轮转交，此条一并交出」
> （`剧本.ts` 的 `S00005-3-1`，改动处带注释）。
>
> **这恰好把 ⑦ 这个问题从「设计里没定义」推到了「代码必须给出一个答案」**：
> 上面两个选项里，实现选的是「**报备不提交**」—— 所以「本轮处置」里那条
> 已不能写「已报备」，只能写「一并交出」。⑦ 的规则空白仍在（推理见下），
> 但演示剧本已经不再回避它。

- 如果 **报备照提交**：对话都转出去了，报备给谁审批？
- 如果 **报备不提交**：那「本轮处置」里写着「已报备」就是假的。

同类问题：**转交的交接包里，要不要带上这一轮 AI 已经直发的消息？**
（剧本里 AI 已经发了两条，转交后新客服看到的上下文里有没有这两条？）

### ⑧ G2 说「拦的是句式不是词」，实现是查词

> `guards.py`：G2 边界 —— 措辞本身没被禁，但形状是「把话说死」。
> **比 G1 宽，因为它拦的是句式不是词。**

但实现是 `if w in 话术` 遍历两个硬编码元组（硬组 8 词 ＋ 软组 7 词，共 15）
—— **和 G1 的子串扫描机制完全同构**。
两者唯一的区别是词表来源（G1 的词来自口径表、带编号；G2 的词是硬编码的）。

所以「G1 最硬 / G2 更宽」这个区分在机制上站不住。**真正拦句式的只有 `G2越权`
那一条正则**（匹配「我赔你」「退50元」这类结构）。

**连带后果**：G2 里「一定」「必须」「随时」「永远」「无条件」这些词在中文里分布极广
（「一定要试试」「必须给您补上」），而 G2 命中直接判**高**严重度 → **直接阻断 →
触发重生成**。这会带来大面积重生成。

> **2026-09-29 更正：这条后果代码已经处理掉了。** 上面那五个词现在归 `G2绝对化软`，
> 判**中**，`是否放行` 只有「高」才拦。代码注释把理由写明了：
> 「判高会让大面积正常话术被阻断、反复重生成。软组只记录」。
> 判高的只剩 `G2绝对化硬` 八个 —— 绝对／100%／百分之百／包退／包换／包赔／永不／绝不。
>
> 但这条矛盾**本身仍然成立**：它说的是「自称拦句式、实为查词」，机制层面没变 ——
> 变的只是误伤面。真正拦句式的仍然只有 `G2越权`。

### ⑨ 「依据列全是为了证明没有遗漏」和 top-K 召回矛盾

> 依据清单的设计意图：**列全是为了证明没有遗漏**（用上的和没用上的都列出来）

但非结构化来源（商品属性表、先例库）靠**向量检索**，而向量检索天然是 top-K 截断的。
**你能证明的只有「召回的这批里没有遗漏」，证明不了全集没有遗漏。**

> **2026-10-06 追记：上面这段的两个例子，现在都不成立。** ① 商品属性表是按货号
> **精确连接**（`表.get(货号)`，20 行全查），**从来就没有 top-K** ——「非结构化 →
> 向量检索」这一半从落地起就没成立过；③ 先例库现在**确实**走向量召回（取 3 条），
> 但它**不进六源**、不在「依据清单」里（走 prompt 第 6 块）—— 所以「列全是为了
> 证明没有遗漏」这句和向量截断，在这套实现里**碰不上面**（六源是封闭集合、全查，
> 正走的是下面那句「遍历全部来源」的路）。**还剩的限度在 ③ 自己身上**：「召回了
> 3 条」不等于「③ 里每一条都看过了」，演示时要主动说这一层（记在
> `rules/sources.py` 的文档串里）。

要真证明没遗漏，得对每个主张遍历全部来源 —— 那是全表扫描，不是检索。
而且「没用上的」这一栏的语义也含糊：是「召回了但没用」还是「存在但没召回」？
前者能列，后者列不出来。

### ⑩ 「带反馈重生成」不是万能兜底

设计：**命中 → 带反馈重生成 → 再命中 → 降级成「需要话术」交给客服手写。**

两种情况兜不住：

- **死循环**：节点 5 检索为空 → G3 判「没有任何依据支撑」（高危）→ 重生成 →
  检索还是空 → 再拦。**重生成改变不了「没有依据」这个事实。**
- **修不了的事实错误**：G4 命中「话术说已经补发了，但办过什么里没有」——
  这是**事实错误**，重生成只能让模型换种说法不承认做过，或者干脆不提，
  但真正该做的是回去查工单。**这类命中重生成是错的动作。**

还有降级终点本身的问题：降级成「需要话术」，但「需要话术」这个形态
**要渲染的就是 `advice.话术`**。**话术恰恰是生成失败的那个东西。**
降级后交给客服的是什么？空话术？还是把最后一次被拦的话术连着命中项一起给客服看？

> **2026-09-29 更正：`话术` 在后端是可选字段（`话术?: string`），
> `AdviceCard` 是「有就渲染」**（`{advice.话术 ? <p>…</p> : null}`），不是「要求有」。
> 所以「降级成一个没有话术的 `需要话术` 卡」在类型上是合法的，不会当场报错 ——
> 客服看到的就是一张只有命中项的卡。**这正是问题所在**：类型不报错，
> 界面也渲染得出来，但「让客服照着写」这个功能没实现。
>
> **顺带答一半**：降级后给客服什么，`pipeline.降级结果` 已经定了 ——
> 最后被拦的原文 ＋ 命中原因 ＋ 依据。⑩ 剩下的空白是「前端怎么呈现它」，
> 以及上面那条死循环（无依据 → 重生成 → 还是无依据）依旧没有出口。

### ⑪ AI 写的话过四道闸门，人写的话过一道

| 谁写的 | 过哪些校验 |
|--------|-----------|
| **AI 生成** | G1 禁语 + G2 边界 + G3 来源可查 + G4 防矛盾 |
| **客服手写** | 只有 `查禁语()` = **G1 一道** |

确认条只查禁语。所以客服完全可以手写「保证明天一定给您补发」（G2 该拦的越权承诺）、
手写「会在 24 小时内发出」（G3 该拦的编造数字）、把 AI 刚说过的话再发一遍
（G4 该拦的重复）。

**而「仍然发送」这个按钮的存在，说明设计上认为客服是会越过口径的。**
既然承认人会越界，只给人一道最没用的闸门（查表，人工最清楚）就说不通 ——
真正该给人看的是 G2 和 G4。

### ⑫ 「判定必须可重放」和「链路里有 LLM」不能共存

> `triggers.py`：判定必须可重放，同一份输入跑两遍得出一模一样的结论，
> 否则演示时没法解释。

这条要求在规则层是靠**时间外部注入 + 稳定排序**实现的，做得很干净。
但链路上有两次模型调用（拆主张、话术生成），**同样的输入未必出同样的输出**。

于是「可重放」只在规则层成立，到模型层就断了。而**留痕要能解释的恰恰是模型那两步**
（为什么拆出这三条主张、为什么这么措辞）。规则层可重放解决不了这个问题。

**要么**接受「留痕记的是结果不是过程」，**要么**模型那两步也得有确定性的替代
（比如主张拆解退回规则模板）。

## C 档 · 定义缺失

### ⑬ 「三层判定」的三层没有定义

名字出现在注释里（`triggers.py`：「这些事实该判成哪种输出，是 `pipeline.py` 里
三层判定的事」），但没有任何地方说三层是哪三层、每层判什么、规则表长什么样。
这是**整条流程唯一的核心判定环节**，它定义不了，上面七个节点和下面三个节点就接不上。

### ⑭ 主张的粒度和主键都没定义

- **粒度**：「孕妇能否用」和「含乙醇」是两条还是一条？粒度决定处置条数。
- **主键**：主张文本被当成了唯一键（React `key={d.主张}`），文本相同就冲突。

### ⑮ 口径表是草稿，而 G3 拿它当「真数」的出处

`koujing.json` 元数据自己写着原表标题是「**待改错**」，待核对项三条：
K03 退款到账天数、K05 补发 48 小时、K07 价保时效。

而 G3 的机制是「话术里的数字必须能追到依据或**可引用文本**」，
可引用文本就是口径表的「可以说」和「标准话术」。

**于是闸门在为一批没确认的数字背书**：话术说「48 小时内发出」，
G3 查口径表 K05 里有「48 小时」→ 放行。**但那个 48 小时本身还没确认。**

### ⑯ `Evidence.序号` 的语义不自洽

看起来是固定的来源编号（①商品属性表 ②口径表 ③先例库 ④订单 ⑤工单 ⑥…），
但对不上：

- `S00003` 里 `⑤` 用了两次，**两条出处都是不良反应工单**（`data/index.ts` 的两处）
- 剧本第六步 `⑦` 指口径表 K20，但第五步 `⑦` 指顾客情况

**是「这一卡内的第几条」还是「全局来源 ID」？两种用法混在一起了。**

> **2026-09-29 更正：上面两个例子都举错了，但结论没错。**
>
> - `⑤` 的那两处**不矛盾**：同一个来源出多条引用是合法的、也是预期内的
>   （口径表同时命中 K06 和 K20 是正常事）。**按来源计数、按条目列出**，
>   两处都规规矩矩落在「⑤ 不良反应工单」上。我原先读成了两个来源。
> - `⑦` **一次都没出现过**。逐字符数过 `frontend/src/data/` 三个文件：
>   ①10 ②8 ③6 ④2 ⑤4 ⑥3 **⑦0**。剧本第六步的 K06 和 K20 都挂在 `②` 上。
>
> 所以 ⑯ 的真实状态是：**编号已经是全局来源 ID 了，没有第二种用法** ——
> `Evidence.序号` 的类型是 `六源` 这个封闭联合类型（`types/index.ts`），
> 想塞第七个来源进去**编译就过不了**。这条从「语义不自洽」降级成「我读错了」。

### ⑰ 顾客情况有循环依赖

顾客情况里那一行：

```
{ 标签: '答应过什么', 值: '9/26 承诺「今天答复」', 备注: '时限：9/26 24:00', 警示: '已逾期 2 天' }
```

- `警示: '已逾期 2 天'` 是 **H3 的输出**
- H3 的输入 `承诺时限` 又**来自这一行**

**顾客情况 → H3 → 警示 → 顾客情况。** 谁先算？

### ⑱ G4 的「已发出」包含 AI 直发吗？

`G4防矛盾(话术, 已发出=[...])` **没定义 `已发出` 装的是什么。**

- **不含 AI 直发** → AI 可能对着同一个顾客把同一句话说两遍
