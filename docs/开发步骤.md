## 二、一条原则

**先打通，再加固。**

不要把「拆主张准确率」打磨到 90% 才开始写接口 —— 那样到第五天你还没有一个能演示的东西。
反过来：三步模型调用（拆主张 / 依据检索 / 话术生成）的**输入输出形状是固定的**，
先用笨办法顶上去，接口就能先写完、前端就能先接上。**换实现的时候前端一行不用改。**

唯一不能先凑合的是**契约**。字段名改一次，前端跟着改一遍。

## 三、步骤

### 步骤 0（半天）· 定契约，不写逻辑

先写 `backend/app/api/schemas.py`，把「一句话进来 → 右栏出什么」的 JSON 形状定死。

**为什么第一步是这个而不是接口。** 前端右栏的每个字段都要从这里来。契约定在前面花半天，
定在后面每次改动都要前后端各返工一遍。而且有了它，前端可以**先接 mock**，
不必等后端写完 —— 两条线并行。

产出：

- `backend/app/api/schemas.py` —— 请求/响应 pydantic 模型
- `docs/接口契约.md` —— 人读版，带完整样例 JSON

完成标准：`frontend/src/types/index.ts` 里的 `Session / Advice / Disposition / StateRow /
Evidence / GuardHit` 每一个字段都能在 schemas 里找到**逐字对应**的（字段名保持中文，
和现有风格一致，别引入映射层）。

**`依据` 这一条要在契约里定死两件事**（演示数据里都真实出现过，不定就是前后端各写一套）：

1. **一个来源可以有多条引用。** 口径表同时命中 K06「不良反应处理」和 K20「投诉与升级」
   是正常的 —— 两条都要返回、都要显示，**别按来源去重**。（计数时才按来源折算，
   见 `AdviceCard.EvidenceList`。）
2. **没命中的来源返回不返回。** 现在的做法是：**后端只返回查到的，前端按六源补空位**。
   这样 `N/6 源命中` 和「另 N 源无记录」在任何后端实现下都成立，也不会漏列。

### 步骤 2（2–3 天）· 核心接口 `POST /api/判定`

**这是整个项目的主接口。** 前面两个都只是它的铺垫。

#### 请求

```json
{
  "会话ID": "S00001",
  "当前时间": "2026-09-28T11:04:00",
  "轮次": null
}
```

- `当前时间` 可省，省了取服务器时间。**显式传是为了回放** —— 演示时要能把「9/26 承诺」
  这条历史记录当成「现在」重跑一遍，见 `triggers.py` 模块文档串里「可重放的边界」。
- `轮次` 可省，省了取最后一轮。补历史轮次是为了让「本轮处置」能逐轮回看。

**消息不从请求里传，后端自己按 `会话ID` 查。** 前端持有完整消息流是个诱惑（它现在就有），
但那样「判定」就不是服务端的事了，留痕也无从记起。

#### 响应

```json
{
  "会话ID": "S00001",
  "轮次": 3,
  "顾客情况": [
    { "标签": "这是谁",     "值": "王女士 · 88VIP" },
    { "标签": "答应过什么", "值": "9/26 承诺「今天答复」",
      "时限": "2026-09-26T23:59", "警示": "已逾期 2 天" }
  ],
  "安全事件": [],
  "触发": [
    { "编号": "H1", "名称": "风险", "严重度": "高", "证据": ["刺痛", "投诉"] },
    { "编号": "H3", "名称": "逾期", "严重度": "高", "证据": ["…已过 2 天"] }
  ],
  "本轮处置": [
    { "id": "S00001-3-1", "轮次": 3, "主张": "用后泛红刺痛",
      "输出": "转交", "说明": "H1 风险命中：刺痛" }
  ],
  "主卡": {
    "形态": "有风险",
    "判断": "这次需要「转交」",
    "标题": "⚠ 顾客报告不良反应 · 情绪升级",
    "说明": ["…"],
    "风险标签": "⚠ 顾客已登记不良反应 · 情绪升级",
    "依据": [ { "序号": "⑤", "出处": "不良反应工单 T0012", "摘要": "…", "用上": true } ]
  },
  "已代发": [],
  "闸门": []
}
```

#### 内部流水线

现成的接上，缺的插进去。**这个顺序是定的**，每一步的输入都来自前面：

| # | 步骤 | 状态 | 在哪 |
| --- | --- | --- | --- |
| 1 | 切轮 | ✅ | `pipeline.切轮` |
| 2 | 装配顾客情况（含 `时限`） | ⚠️ 算法有，**「值」从哪来没写** | `pipeline.组装顾客情况` |
| 3 | 扫输入安全 | ✅ | `inbound.扫输入` |
| 4 | 硬触发 H1–H4 | ✅ **命中 H1/H2/H4 即整轮转交，三层整个不跑** | `triggers.硬触发` |
| 5 | **拆主张** | ❌ 连规则版都还没有 | LLM |
| 6 | 三层判定 | ✅ **已按 v8 重写**：① 查六源 ② 查权限矩阵 ③ 话怎么说 | `pipeline.三层判定` ＋ `permissions.查权限` |
| 7 | 收敛 | ✅ | `pipeline.收敛` |
| 8 | **依据检索** | ❌ 六源只有契约（`sources.py`），**没有查询实现** | pgvector |
| 9 | **话术生成** | ❌ 先返回 `标准话术` | LLM |
| 10 | 过闸门 + 重生成 | ✅ | `guards` |
| 11 | 落留痕 | ❌ 内存即可 | 存储 |

> **现状：`AI直发` 实际不可达。** `三层判定` 的 `六源` 参数默认 `None` →
> 每条主张取 `空六源结果` → 第 1 层永远报「查不到」→ 一律落到**客服点发送**。
> 这是**先重构判定层、后接数据层**的安全依据（判错不会让话发出去），
> 但也意味着：**在数据层接上之前，第 3 层和权限矩阵都跑在空输入上** ——
> 它们有测试、但还没在真数据上走过一遍。别把「测试全绿」读成「链路通了」。

**第 5、8、9 三步先用最笨的实现：**

- **拆主张**：按 `，。、` 切分 + 关键词表。只求跑通。
- **依据检索**：返回空列表。这时 G3 会判「没有任何依据」，正好逼着你把降级路径走通。
- **话术生成**：返回口径表的 `标准话术` 字段 —— 它是现成的，而且天然不含禁语。

第 2 步的「值从哪来」要单独说：五行里「这是谁」「这单」查订单/会员表，「这次要什么」来自
拆主张的结果（所以它其实排在第 5 步之后），「答应过什么」「办过什么」查工单。
**先用写死的演示值把这行填上**，等步骤 3 的检索做好了再回头接。

#### 完成标准

拿演示剧本第六步（不良反应 + 投诉 + 逾期）打这个接口，返回的东西要和
`frontend/src/data/剧本.ts` 的**第六步**那一段（认 `第六步` 那条注释，当前在 347–409 行）
**逐字段对得上** —— 六条处置、`主卡.形态 = '有风险'`、顾客情况第三行带「已逾期 2 天」。

> 认注释别认行号：这个文件还在改，行号会漂（这段原来写「第 356 行起」，现在已经偏了 9 行）。

对得上，说明前端可以整段删掉假数据、改读接口了。

### 步骤 3（2–3 天）· 把六个笨实现逐个换掉

**先纠正一处**：本节原来写「三个笨实现」，数的是**流水线**上的三个
（拆主张／依据检索／话术生成）。但规则层里另**有三个模型位置**
（代码自己的文档串写明的：`涉个体差异` 说自己是「链路里的第三个」，
前两个是 `认口径` 和 `认权限`），一个都没算进来：

| 模型位置 | 现在是什么 | 在哪 |
| --- | --- | --- |
| `认口径` | 关键词匹配 —— **实测六条主张只认中一条** | `pipeline.py` |
| `认权限` | 关键词匹配（22 条里 16 条带 `可认` 关键词） | `permissions.py` |
| `涉个体差异` | 关键词匹配，**主张那一遍是临时兜底** | `pipeline.py` |
| 拆主张 | **连规则版都还没有** | 待建 |
| 依据检索 | 只有六源契约（`sources.py`），没有查询 | 待建 |
| 话术生成 | 待建 | 待建 |

加起来是**六个**。前三个是判定层的**输入** —— 认错了口径就是依据挂错、
认错了权限就是去向判错，而且**不会报错**，只会静静地判歪。

`涉个体差异` 那处还有个**临时状态要记**：它现在先读顾客情况小卡、再退回从主张抠
关键词，理由是装配层还没有、`顾客情况` 默认是空的（只读小卡等于这道判据永远
返回 False）。**等装配层能给结构化字段了，把主张那一遍删掉。**

按**风险从高到低**换。

#### 3a · 依据检索上 pgvector（1–2 天）—— 唯一有真实工程量的一块

先做这个，不是因为它最重要，是因为它**最可能出意外**（建表、embedding 批次、
维度不匹配、中文分词）。留足时间给它。

- `backend/app/检索/建索引.py` —— 商品属性表 / 先例库切块 → embedding → 入库
- `backend/app/检索/召回.py` —— 主张 → top-K
- 口径表只有 20 条，**不走向量**，每次全量塞进 prompt。向量召回在 20 条上是负优化。

**召回条数写进留痕，六源的有／无写进 `依据` 列表** —— 这是两件事，别混：
top-K 召回了几条是检索质量的证据，进留痕；而 `依据` 列表的骨架是**六源这个封闭集合**，
逐个来源报「有记录／无记录」。

「列全证明没有遗漏」这句话**站得住**，但只在**六源**的粒度上 —— 六源封闭，逐个报有／无
是可穷举的。源内部做不到：① 商品属性表和 ③ 先例库走 top-K，只能证明「召回的这批里没漏」。
演示时主动把这两层分开说，评委一定会问这个。详见 `types/index.ts` 里 `Evidence` 的注释。

#### 3b · 拆主张换 LLM（半天）

- `backend/app/llm/客户端.py` —— openai 兼容客户端，`base_url` + `model` 走配置
  （依赖已经声明了，换模型只改这两个值）
- `backend/app/llm/拆主张.py` —— prompt + 结构化输出
- `backend/tests/test_拆主张.py` —— 拿演示剧本的 12 条买家消息做回归

prompt 要点：**要求拆出「顾客的一个诉求」这个粒度的主张，不是风险点**。
判据在 `types/index.ts` 的 `Disposition` 注释里：「用了你们精华脸刺痛，另外赠品也没收到」
是两条主张。同一诉求的多个触发**不拆**，`输出` 取高的那个。

#### 3c · 话术生成换 LLM（半天）

- 输入：主张 + 依据 + 口径的 `可以说` / `标准话术` + 顾客情况 + 触发
- 接上 `guards.过闸门` → `guards.重生成可行` → 重试（**最多 2 次**）→ `pipeline.造降级`

**重试次数封顶这条是硬要求**，理由见 `guards.重生成可行` 的文档串：G3「没有依据」和
G4「谎称已做」两类判 `可重生成=False`，重生成只会把模型困在原地转圈，
或者教它换个说法把同一个谎绕过去。

### 步骤 4（2 天）· 动作接口

四个动作对应前端的四个按钮。**它们不是「改个状态」那么简单，每个都要写留痕。**

```
POST /api/会话/{id}/发送        { 话术, 采用的处置id[] }
POST /api/会话/{id}/报备        → 生成工单号（规格 §7，客服零填写）
POST /api/会话/{id}/转交        → 交接包 = 顾客情况 + 依据 + 触发 + 已发出的话
POST /api/会话/{id}/草稿检查     { 草稿 } → GuardHit[]
```

`草稿检查` 单独拎出来是有原因的：客服把 AI 的话改了几个字之后，禁语**必须重新查**。
前端 `Composer.tsx` 现在用的是本地 `查禁语()`，接口化之后两边才是同一份规则 ——
否则演示时会出「本地说不违规、后端说违规」这种最难解释的 bug。

`发送` 收 `采用的处置id[]` 是为了记清「这条话术是兑现哪几条主张的」。
`Disposition.id` 就是为这个加的（见 `types/index.ts`）。

## 四、时间不够时砍什么

**必须有的三件**（没有就不能叫「数据共情者」）：

1. `POST /api/判定` —— 主接口
2. 依据检索 —— 右栏「依据清单」是全部说服力所在
3. `已代发` 区块 —— 少了它，「AI 直发」在右栏是隐形的，客服不知道刚才有句话以他的名义发出去了

**可以砍的三件**：

1. `留痕` 的 UI（接口留着，界面不做）
2. `草稿检查` 接口化（先用前端本地规则，说清楚就行）
3. 向量检索的**增量更新**（演示数据是静态的，全量重建够用）

## 五、规格 v8 带来的新增工作

v8 里有两节是**设计增量**（不是修 bug），各自带出新的实现要求。

### 5a · 权限矩阵（v8 §六）—— ✅ **已实现**

三层判定的第 ② 层「这件事归谁办」查的就是它。落在 `backend/app/rules/permissions.py`。

**本节原来拟的形状是拍脑袋写的，规格里并没有 —— 实际实现比它宽，别照旧的写：**

| | 本节原拟 | 实际实现 |
| --- | --- | --- |
| 数据条数 | 21 行 | **22 条**（在权限内 9 ＋ 超额度报备 5 ＋ 超额度转交 1 ＋ 必须转交 7） |
| `权限条目` 字段 | 5 个 | **13 个**（多出 `编号` `升级说明` `可认` `关键词` `限额件数` `限额金额` `需质量问题` `超出后去向`） |
| `查权限` 返回 | `str`，三态 | **`权限判定` 对象**；去向是**五态**：在权限内／报备／转交／判不了／未列明 |
| 「超额度」 | 当成一个去向 | **不是一个去向** —— 改判到该条目自己的 `超出后去向` |
| 数据放哪 | 没写 | **硬编码在模块里的 tuple**，不读任何外部数据文件 |

最后两行值得单独记：`判不了`（件数／金额／是不是质量问题这些**条件**查不到）落到**报备**，
不进专家线；矩阵里 16 条带 `可认` 关键词、6 条认不出 —— 认不出落到 `未列明`，
**和 `判不了` 不是一回事**（`未列明` 继续走第 3 层，它管的是要授权的事，
不是「客服能聊什么」的白名单）。

本节列的**三条容易抄错 —— 三条都抄对了**，留在代码里当路标：

- **§6.2b 只有一行**（`X01` 赠品追加超额度，`可认=False`），和新增的
  「会员权益加赠补发」（`L04`，在权限内）**方向相反**，区别在「符不符合已有规则」，
  不在「是不是会员权益」。`L03` 那行配了注释明说「别顺手改成报备」。
- **价差补差**（`L07`）是 `限额="无额度，按平台规则自动核算"`，**`限额金额` 留 `None`**
  —— 没按旧版写死金额。
- **「48 小时发出」所有层级都一样**：代码里**根本没有按层级区分这个数字的字段**，
  也就没有「一线特权」这个写法。

### 5b · 转交对客话术（v8 §七）—— ⚠️ **实现有、测试缺**

6 类转交各配一句话术，**走 ② 客服点发送**（因为含时限，含时限就是承诺）。
落在 `backend/app/rules/handover.py` —— **文件名不是本节原来写的 `转交话术.py`**。

形状和本节拟的一致：`转交话术表: dict[str, 转交话术]`，6 个键是
`不良反应 / 不良反应已就医 / 风控核实 / 物流丢件赔付 / 投诉升级 / 承诺逾期`。
另有 `H3分类话术`（产品／物流／公关 → 都指向「承诺逾期」）。

**三条硬边界写了，但写成了「模块导入时的自检」，不是测试：**

| # | 硬边界 | 自检里有没有 | 测试里有没有 |
| --- | --- | --- | --- |
| 1 | 「24 小时」只能修饰**回访**，不能修饰**解决** | ✅ `校验转交话术()` | ❌ |
| 2 | 风控类、丢件类**禁止给具体时限** | ✅ 同上 | ❌ |
| 3 | 这些话术**不得走 ① AI 直发** | ✅ 同上 | ❌ |

> ⚠️ **而且这段自检从来没被执行过。** 它在 `handover.py` 模块导入时跑
> （`raise 转交话术越界`），但 `tests/` 下**没有任何文件 import handover** ——
> pytest 一次都没触发过它。三条硬边界现在是**一段没被验证过的代码**，
> 不是三条被证明成立的约束。
>
> 补法很便宜：加一个测试文件 import 它（自检随之就跑起来了），再给三条各写一条断言。
> **别只在文档上记一笔就过** —— 这是当前唯一一处「写了校验但没人验证」的地方。

**一处实现偏离要记着**：本节原话说第 3 条「和 `pipeline.口径输出表` 是同一个机制，
别新写一套 —— 把转交话术也当成一类主张进同一张输出表」。
**实际没走这条路**：`handover` 是独立模块，`pipeline` 没有 import 它，
`口径输出表` 也已退役。所以「不得 AI 直发」这条目前**只靠 handover 自己的自检**，
不在判定层的路径上。要让它真正生效，得把 `handover` 接进 `三层判定`。
