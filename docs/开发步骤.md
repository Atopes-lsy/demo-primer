# 开发步骤 —— 从现在的代码到能演示的东西

## 一、先看清现在有什么

**已实现**（`backend/app/rules/`，纯规则、无模型、43 个测试通过）：

| 模块 | 职责 | 状态 |
| --- | --- | --- |
| `inbound.py` | 输入安全层，注入/违规拦截，PII/辱骂标记 | ✅ |
| `triggers.py` | 硬触发 H1–H4 | ✅ |
| `koujing.py` | 口径表加载 + 「可以说」与禁语互斥校验 | ✅ |
| `guards.py` | 出站闸门 G1–G4 + `重生成可行` | ✅ |
| `pipeline.py` | 三层判定、收敛、切轮、顾客情况、降级 | ✅ |

**没有的 —— 这才是接下来要写的：**

| 缺什么 | 没有它会发生什么 |
| --- | --- |
| 任何 HTTP 接口 | 前端右栏只能读死数据，判定层再对也没用 |
| **拆主张** | 三层判定的输入，没有它整条链路空转 |
| **依据检索** | 话术没料，G3 每次都判「没有任何依据」 |
| **话术生成** | 主卡没有正文，只剩一堆状态 |
| **权限矩阵** | 规格第六节整节，代码里完全没有 —— 而它是三层判定第 ② 层的全部输入 |
| 存储 | 留痕、会话、工单都没地方放 |
| 前端接接口 | 演示的是「前端写死的剧本」，不是「系统跑出来的」 |

> **⚠️ 2026-09-29 追记：规格 v8 到了，发现四处「代码和规格理解不同」——
> 不是缺功能，是同一件事被理解成了两回事。** 详见 [规格v8对齐.md](规格v8对齐.md)
> 第三节。**其中两处（H2 的去向、三层判定按哪版）要先找队长拍板，不是编码问题。**
> 拍板之前，下面步骤 2 里的 `三层判定` 和 `触发输出表` 先别动。

**实测暴露的问题**：`pipeline.认口径` 拿演示剧本第六步的六条主张试，只认中一条 ——
`孕妇能否用` 认不到 `K01 孕期/哺乳期使用`。它是关键词匹配，是链路里的一个**模型位置**的占位。
不换掉，「依据：口径表 Kxx」这句话就是不可信的，而它是右栏最有说服力的那行字。

## 二、一条原则

**先打通，再加固。**

不要把「拆主张准确率」打磨到 90% 才开始写接口 —— 那样到第五天你还没有一个能演示的东西。
反过来：三步模型调用（拆主张 / 依据检索 / 话术生成）的**输入输出形状是固定的**，
先用笨办法顶上去，接口就能先写完、前端就能先接上。**换实现的时候前端一行不用改。**

唯一不能先凑合的是**契约**。字段名改一次，前端跟着改一遍。

## 三、步骤

### 步骤 0（半天）· 定契约，不写逻辑

先写 `backend/app/api/schemas.py`，把「一句话进来 → 右栏出什么」的 JSON 形状定死。

**为什么第一步是这个而不是接口。** 前端右栏的每个字段都要从这里来。契约定在前面花半天，
定在后面每次改动都要前后端各返工一遍。而且有了它，前端可以**先接 mock**，
不必等后端写完 —— 两条线并行。

产出：

- `backend/app/api/schemas.py` —— 请求/响应 pydantic 模型
- `docs/接口契约.md` —— 人读版，带完整样例 JSON

完成标准：`frontend/src/types/index.ts` 里的 `Session / Advice / Disposition / StateRow /
Evidence / GuardHit` 每一个字段都能在 schemas 里找到**逐字对应**的（字段名保持中文，
和现有风格一致，别引入映射层）。

### 步骤 1（1 天）· FastAPI 骨架 + 数据装载

文件：

- `backend/app/main.py` —— app、CORS、统一异常处理
- `backend/app/data/装载器.py` —— 把 `业务数据.xlsx` 读进内存（原始文件在仓库外的 Downloads）
- `backend/app/api/deps.py` —— 依赖注入，装载器单例

**第一个要写的接口是这个，不是判定：**

```
GET /healthz          → {"ok": true}
GET /api/会话列表      → Session[]  （左侧列表要的字段）
```

**为什么先写这两个这么简单的。** 它们验证的是「前后端能通」这件事本身 —— Vite 代理配没配对、
CORS 过不过、中文经不经得起 JSON 往返。这些坑在五分钟的接口上暴露，比在判定接口上暴露便宜得多。
不要等写到判定接口才发现跨域没配。

完成标准：

```bash
curl localhost:8000/api/会话列表 | head
```

返回演示数据；把 `App.tsx` 的左侧列表换成 fetch 它，界面照样显示。

### 步骤 2（2–3 天）· 核心接口 `POST /api/判定`

**这是整个项目的主接口。** 前面两个都只是它的铺垫。

#### 请求

```json
{
  "会话ID": "S00001",
  "当前时间": "2026-09-28T11:04:00",
  "轮次": null
}
```

- `当前时间` 可省，省了取服务器时间。**显式传是为了回放** —— 演示时要能把「9/26 承诺」
  这条历史记录当成「现在」重跑一遍，见 `triggers.py` 模块文档串里「可重放的边界」。
- `轮次` 可省，省了取最后一轮。补历史轮次是为了让「本轮处置」能逐轮回看。

**消息不从请求里传，后端自己按 `会话ID` 查。** 前端持有完整消息流是个诱惑（它现在就有），
但那样「判定」就不是服务端的事了，留痕也无从记起。

#### 响应

```json
{
  "会话ID": "S00001",
  "轮次": 3,
  "顾客情况": [
    { "标签": "这是谁",     "值": "王女士 · 88VIP" },
    { "标签": "答应过什么", "值": "9/26 承诺「今天答复」",
      "时限": "2026-09-26T23:59", "警示": "已逾期 2 天" }
  ],
  "安全事件": [],
  "触发": [
    { "编号": "H1", "名称": "风险", "严重度": "高", "证据": ["刺痛", "投诉"] },
    { "编号": "H3", "名称": "逾期", "严重度": "高", "证据": ["…已过 2 天"] }
  ],
  "本轮处置": [
    { "id": "S00001-3-1", "轮次": 3, "主张": "用后泛红刺痛",
      "输出": "转交", "说明": "H1 风险命中：刺痛" }
  ],
  "主卡": {
    "形态": "有风险",
    "判断": "这次需要「转交」",
    "标题": "⚠ 顾客报告不良反应 · 情绪升级",
    "说明": ["…"],
    "风险标签": "⚠ 顾客已登记不良反应 · 情绪升级",
    "依据": [ { "序号": "⑤", "出处": "不良反应工单 T0012", "摘要": "…", "用上": true } ]
  },
  "已代发": [],
  "闸门": []
}
```

#### 内部流水线

现成的接上，缺的插进去。**这个顺序是定的**，每一步的输入都来自前面：

| # | 步骤 | 状态 | 在哪 |
| --- | --- | --- | --- |
| 1 | 切轮 | ✅ | `pipeline.切轮` |
| 2 | 装配顾客情况（含 `时限`） | ⚠️ 算法有，**「值」从哪来没写** | `pipeline.组装顾客情况` |
| 3 | 扫输入安全 | ✅ | `inbound.扫输入` |
| 4 | 硬触发 H1–H4 | ✅ | `triggers.硬触发` |
| 5 | **拆主张** | ❌ 先用规则顶 | LLM |
| 6 | 三层判定 | ✅ | `pipeline.三层判定` |
| 7 | 收敛 | ✅ | `pipeline.收敛` |
| 8 | **依据检索** | ❌ 先返回空 | pgvector |
| 9 | **话术生成** | ❌ 先返回 `标准话术` | LLM |
| 10 | 过闸门 + 重生成 | ✅ | `guards` |
| 11 | 落留痕 | ❌ 内存即可 | 存储 |

**第 5、8、9 三步先用最笨的实现：**

- **拆主张**：按 `，。、` 切分 + 关键词表。只求跑通。
- **依据检索**：返回空列表。这时 G3 会判「没有任何依据」，正好逼着你把降级路径走通。
- **话术生成**：返回口径表的 `标准话术` 字段 —— 它是现成的，而且天然不含禁语。

第 2 步的「值从哪来」要单独说：五行里「这是谁」「这单」查订单/会员表，「这次要什么」来自
拆主张的结果（所以它其实排在第 5 步之后），「答应过什么」「办过什么」查工单。
**先用写死的演示值把这行填上**，等步骤 3 的检索做好了再回头接。

#### 完成标准

拿演示剧本第六步（不良反应 + 投诉 + 逾期）打这个接口，返回的东西要和
`frontend/src/data/剧本.ts` 第 356 行起那一段**逐字段对得上** —— 六条处置、
`主卡.形态 = '有风险'`、顾客情况第三行带「已逾期 2 天」。

对得上，说明前端可以整段删掉假数据、改读接口了。

### 步骤 3（2–3 天）· 把三个笨实现逐个换掉

按**风险从高到低**换。

#### 3a · 依据检索上 pgvector（1–2 天）—— 唯一有真实工程量的一块

先做这个，不是因为它最重要，是因为它**最可能出意外**（建表、embedding 批次、
维度不匹配、中文分词）。留足时间给它。

- `backend/app/检索/建索引.py` —— 商品属性表 / 先例库切块 → embedding → 入库
- `backend/app/检索/召回.py` —— 主张 → top-K
- 口径表只有 20 条，**不走向量**，每次全量塞进 prompt。向量召回在 20 条上是负优化。

**召回条数必须写进留痕和 `依据` 列表。** 这是「列全是为了证明没有编造」这句话能不能说出口的
前提 —— 见 `types/index.ts` 里 `Evidence` 的注释：能承诺的是「没有编造」，
不能承诺的是「没有遗漏」，因为召回天然是 top-K 截断的。演示时评委一定会问这个。

#### 3b · 拆主张换 LLM（半天）

- `backend/app/llm/客户端.py` —— openai 兼容客户端，`base_url` + `model` 走配置
  （依赖已经声明了，换模型只改这两个值）
- `backend/app/llm/拆主张.py` —— prompt + 结构化输出
- `backend/tests/test_拆主张.py` —— 拿演示剧本的 12 条买家消息做回归

prompt 要点：**要求拆出「顾客的一个诉求」这个粒度的主张，不是风险点**。
判据在 `types/index.ts` 的 `Disposition` 注释里：「用了你们精华脸刺痛，另外赠品也没收到」
是两条主张。同一诉求的多个触发**不拆**，`输出` 取高的那个。

#### 3c · 话术生成换 LLM（半天）

- 输入：主张 + 依据 + 口径的 `可以说` / `标准话术` + 顾客情况 + 触发
- 接上 `guards.过闸门` → `guards.重生成可行` → 重试（**最多 2 次**）→ `pipeline.造降级`

**重试次数封顶这条是硬要求**，理由见 `guards.重生成可行` 的文档串：G3「没有依据」和
G4「谎称已做」两类判 `可重生成=False`，重生成只会把模型困在原地转圈，
或者教它换个说法把同一个谎绕过去。

### 步骤 4（2 天）· 动作接口

四个动作对应前端的四个按钮。**它们不是「改个状态」那么简单，每个都要写留痕。**

```
POST /api/会话/{id}/发送        { 话术, 采用的处置id[] }
POST /api/会话/{id}/报备        → 生成工单号（规格 §7，客服零填写）
POST /api/会话/{id}/转交        → 交接包 = 顾客情况 + 依据 + 触发 + 已发出的话
POST /api/会话/{id}/草稿检查     { 草稿 } → GuardHit[]
```

`草稿检查` 单独拎出来是有原因的：客服把 AI 的话改了几个字之后，禁语**必须重新查**。
前端 `Composer.tsx` 现在用的是本地 `查禁语()`，接口化之后两边才是同一份规则 ——
否则演示时会出「本地说不违规、后端说违规」这种最难解释的 bug。

`发送` 收 `采用的处置id[]` 是为了记清「这条话术是兑现哪几条主张的」。
`Disposition.id` 就是为这个加的（见 `types/index.ts`）。

### 步骤 6（1 天）· 留痕与回放

```
GET /api/会话/{id}/留痕
GET /api/会话/{id}/留痕/{轮次}
```

留痕要能回答的问题（演示时这是加分项）：这一轮为什么判成转交？依据是哪几条？
闸门拦了几次？重生成试了几轮？召回了几条？

## 四、时间不够时砍什么

**必须有的三件**（没有就不能叫「数据共情者」）：

1. `POST /api/判定` —— 主接口
2. 依据检索 —— 右栏「依据清单」是全部说服力所在
3. `已代发` 区块 —— 少了它，「AI 直发」在右栏是隐形的，客服不知道刚才有句话以他的名义发出去了

**可以砍的三件**：

1. `留痕` 的 UI（接口留着，界面不做）
2. `草稿检查` 接口化（先用前端本地规则，说清楚就行）
3. 向量检索的**增量更新**（演示数据是静态的，全量重建够用）

## 五、规格 v8 带来的新增工作

v8 里有两节是**设计增量**（不是修 bug），各自带出新的实现要求。

### 5a · 权限矩阵（v8 §六）

**这是最大的一块缺口。** 三层判定的第 ② 层「这件事归谁办」查的就是它，
代码里一行都没有。

```python
# backend/app/rules/permissions.py
@dataclass(frozen=True, slots=True)
class 权限条目:
    事项: str          # 「补发（不退货）：漏发赠品／少发正装／少件」
    层级: str          # 一线 / 二线 / 专家 / 风控
    限额: str          # 「1 件/单」「≤100 元」「无额度，按平台规则自动核算」
    依据: str          # 「补发换货工单 13/24 由 A 系处理」
    去向: str          # 在权限内 / 报备 / 转交

def 查权限(主张: str, 订单: dict, 顾客情况) -> str:  # 在权限内 / 超额度 / 判不了
    ...
```

数据直接抄 v8 §6.1–6.3 三张表，**21 行**。注意三条容易抄错的：

- **§6.2b 只有一行**（赠品追加超额度），它和 §6.1 新加的「会员权益加赠补发」**方向相反**。
  区别在「符不符合已有规则」，不在「是不是会员权益」。
- **价差补差**已改为「无额度，按平台规则自动核算」，不再卡金额 —— 别按旧版写死额度。
- **「48 小时发出」所有层级都一样**，不是一线的特权。

### 5b · 转交对客话术（v8 §七）

6 类转交各配一句话术，**走 ② 客服点发送**（因为含时限，含时限就是承诺）。

```python
# backend/app/rules/转交话术.py
转交话术表: dict[str, 转交话术] = {
    "不良反应": 转交话术("已为您登记不良反应记录单，专员会在 24 小时内回访跟进。…", "24 小时", "回访"),
    "风控核实": 转交话术("已提交核实工单，有结果我们会第一时间联系您；…", None, None),
    ...
}
```

**三条硬边界要写成测试**，它们是最容易被模型写歪的地方：

1. 「24 小时」只能修饰**回访**，不能修饰**解决** —— 写成「24 小时内解决」是越权承诺
2. 风控类、丢件类**禁止给具体时限**（数据里客服自己都只写「第一时间」）
3. 这些话术**不得走 ① AI 直发**，必须客服点发送

第 3 条和 `pipeline.口径输出表` 是同一个机制，实现时别新写一套 —— 把转交话术
也当成一类「主张」，进同一张输出表。

### 5c · 其余三项小改

| 改什么 | 在哪 | 依据 |
| --- | --- | --- |
| G2 拆成「措辞」和「边界句」两个检查 | `guards.py` | v8 §五 的 G2 是**边界句强制**，代码写的是绝对化词表，不是一回事 |
| 依据清单改成**六源三段式** | `AdviceCard.tsx` | v8 §1.4：命中来源 → `另 3 源无记录` → 未命中六源清单。**默认不折叠** |
| 工单号**按「诉求」去重**，不按「轮」 | 工单生成 | v8 §七：同一诉求因轮次切分被处理多次，也只生成一个号 |

依据改成三段式之后，「列全证明没遗漏」这句话才站得住 —— 它证明的是
**六个来源我都查过了**，不是「召回没有截断」。后者做不到（① 和 ③ 内部走 top-K），
演示时别把两者混着说，会被问住。

## 六、三条容易踩的坑

1. **中文控制台输出**：跑后端命令一律加 `PYTHONIOENCODING=utf-8` 前缀，
   否则中文全是乱码，看测试失败原因都得猜。
2. **`data/` 目录**：现在只有 `koujing.json`。`业务数据.xlsx` 在仓库外的 Downloads，
   装载器要能读**仓库外路径**，别写死相对路径 —— 演示换机器会挂。
3. **`认口径` 先别删**：步骤 3b 把它换成模型之前，它是唯一的兜底。
   换的时候保留 `认口径函数` 这个参数位（`三层判定` 已经是这个签名），别把调用点写死。
